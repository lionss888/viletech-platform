## Принципы правки

1. **Не сжимать в один чеклист** — темы Newman/ML разнести по нескольким `.mdc` (одна забота на файл).
2. **Расширить уже существующие** файлы там, где тема уже заявлена; не пересказывать те же буллеты заново.
3. **Один владелец темы** — если деталь уехала в новое правило, в старом файле остаётся краткий тезис + отсылка к имени правила, без второго полного изложения.
4. Формулировки под **ВЭД-платформу** (роли, заявка/статусы, Provider без ПДн).
5. **Все правила включены всегда:** у каждого `.mdc` в `.cursor/rules/` — `alwaysApply: true` (включая `машинное-обучение.mdc`). Без `globs`-ограничений и без подключения «по запросу».

## 1. Расширение существующих файлов

### [базовые-правила-инструмента.mdc](.cursor/rules/базовые-правила-инструмента.mdc)

Добавить (не дублируя запрет на лишнюю документацию):

- при проектировании сервисов и интеграций опираться на тематические rules (`границы-и-контексты`, `интеграция-и-события`, …);
- при необходимости уточнять детали по PDF в `методология/` и актуальным источникам в сети.

### [лучшие-практики.mdc](.cursor/rules/лучшие-практики.mdc)

**Архитектура** — дописать поверх текущих трёх пунктов:

- дробить на сервисы при независимой скорости изменений / деплоя / масштаба; иначе — модульный монолит с явными пакетами-контекстами;
- детали границ и разреза домена ВЭД — в `границы-и-контексты` (без повторения списка bounded context здесь полным текстом).

**API** — дописать:

- смена статусов и асинхронные реакции — через события/очереди там, где sync REST создаёт жёсткую связность;
- версионирование публичных контрактов; идемпотентность операций с деньгами и повторами;
- детали — в `интеграция-и-события`.

**Безопасность** (новый короткий подраздел или расширение строки про OAuth/JWT):

- роль и зона видимости данных на каждом endpoint; детали ролей ВЭД и ПДн — в `безопасность-ролей-и-данных`.

**Клиент** — без изменений по смыслу (Newman почти не про UI).

**Тренды / ИИ·ML** — заменить размытый буллет на: ML не в MVP процессного ядра; практика — в `машинное-обучение`.

### [правила-построения.mdc](.cursor/rules/правила-построения.mdc)

- после реализации проверять допустимость переходов статусов заявки и права роли на действие;
- (без второго запрета на документацию — он уже есть).

## 2. Новые правила (разбиение Newman / ML)

Все в [`.cursor/rules/`](.cursor/rules/). Frontmatter каждого файла:

```yaml
description: …
alwaysApply: true
```

То же для уже существующих трёх правил (они уже с `alwaysApply: true` — сохранить). Новые пять файлов — тоже только `alwaysApply: true`, без `globs`.

### `границы-и-контексты.mdc`

- хороший сервис: высокая связность внутри, слабая снаружи; обмен в бизнес-терминах;
- ограниченный контекст; разрез под платформу: auth/RBAC, заявка+статусы, compliance, documents, payments/connectors, company/контрагент;
- не шарить БД между сервисами; транзакционные границы при разрезании;
- не плодить сервисы «на будущее» без мотива деплоя/масштаба/команды.

### `интеграция-и-события.mdc`

- критерии интеграции (простые контракты, слабая связность);
- REST + события; заявка/сервис как машина состояний; переходы только явными действиями ролей;
- версионирование API; идемпотентность платежей и ретраев;
- UI не становится единственным носителем бизнес-статусов.

### `безопасность-ролей-и-данных.mdc`

- роли из ТД: User, Internal/External compliance, Manager, Provider;
- принцип минимальных данных на границе; Provider — без ПДн клиента, только реквизиты/инвойсы/платёжные поля;
- authN/authZ на сервисах; данные в покое где хранятся секреты/документы.

### `устойчивость-и-наблюдаемость.mdc`

- корреляция по id заявки в логах/трейсах;
- деградация при сбое провайдера; каскадные сбои;
- идемпотентность и лимиты повторов; кэш/масштаб — по необходимости, не по умолчанию.

### `машинное-обучение.mdc`

- вне MVP ядра (роли, документы, флоу);
- кейсы позже: скоринг/рейтинг, риск заявки, простые текстовые признаки документов;
- train/test или CV, переобучение, пайплайн признаков→модель, метрики до прода;
- отдельная граница от транзакционного платежного пути; fallback на правила/ручной review.

## Что не делать

- Один mega-файл «свод Newman».
- Копировать главы PDF в репозиторий / плодить заметки без запроса.
- Импортировать Bootstrap/Nest/Django rules из `проработка-правил` в этом шаге.
- Дублировать одни и те же списки в `лучшие-практики` и новых файлах.

## Результат

Три существующих правила становятся глубже; пять тематических — по частям Newman/ML; **все восемь** всегда активны по умолчанию; без дублирования тем.
