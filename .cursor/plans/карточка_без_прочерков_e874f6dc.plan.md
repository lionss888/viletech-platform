# Правки карточки заявки

Живой список. Новые пункты дописываются сюда. Исполнение — только после явной команды.

## Пункт 1. Реквизиты организации и контрагента — не прочерки

На карточке заявки `test123` пользователь видит пустые «—», а не сведения.

Где рисуется:

- Блоки «Организация клиента» и «Контрагент» в [vdp/fe/src/components/ved/pages/form-detail-page.tsx](vdp/fe/src/components/ved/pages/form-detail-page.tsx): адрес организации всегда строкой `legalAddress ?? "—"`, контрагент — `{country} · {bank}` и отдельная строка `SWIFT`.
- Та же строка контрагента в проверке участников: [vdp/fe/src/lib/ved/compliance.ts](vdp/fe/src/lib/ved/compliance.ts) (`${country} · SWIFT ${swift}`) — на скрине «Надеждия · SWIFT —».

Почему там прочерк, а не скрытое поле. Маппер [vdp/fe/src/lib/api/catalog-mappers.ts](vdp/fe/src/lib/api/catalog-mappers.ts) подставляет `"—"` в пустые `legalAddress`, `bank`, `swift`. У сида «ООО Пример» нет юридического адреса. У контрагента «Test reel» есть страна «Надеждия», банков нет. Данные не потеряны в API — их нет. Выдумывать адрес или SWIFT нельзя.

Как должно быть для пользователя:

- Есть значение — показать его с понятной подписью (страна, банк, SWIFT, адрес, ИНН).
- Пустое и служебный «—» / «-» не показывать как значение.
- Если реквизита нет — одна короткая фраза, что именно не указано («Юридический адрес не указан», «Банк и SWIFT не указаны»). Не голая черта.
- Строка «Надеждия · —» схлопывается до «Надеждия»; SWIFT-строка не остаётся «SWIFT —».

Не трогать сравнение `counterpartyId !== "—"` и прочие служебные «—» в формах создания. Сентинел в маппере можно оставить; пустоту решать на показе, чтобы не сломать существующие проверки.

Слои: форматтер показа + два блока карточки и `subjectsOf`. Статусы, роли и API не меняются. Unit на заполненные, пустые и уже подставленный «—».

## Пункт 2. «Как собрать путь заявки» — не менеджеру в текучке

Блок на карточке заявки (между степпером и документами) объясняет рычаги, роли процесса и кастом. Менеджеру, который ведёт заявку, это не следующий шаг и не действие по статусу. Текст про сборку маршрута — для того, кто настраивает сценарий.

Сейчас панель [vdp/fe/src/components/ved/ManagerRouteHintPanel.tsx](vdp/fe/src/components/ved/ManagerRouteHintPanel.tsx) монтируется в `form-detail-page` и видна ролям `manager` и `root` (`shouldShowManagerRouteHint`). Отдельного экрана «конструктор сценариев» в кабинете нет. Живой экран настройки участия — «Роли процесса», только суперадмин: [vdp/fe/src/components/ved/pages/process-roles-page.tsx](vdp/fe/src/components/ved/pages/process-roles-page.tsx).

Как должно быть:

- На карточке заявки блока нет ни у менеджера, ни у root. «Следующий шаг» справа остаётся.
- Тот же текст — на экране «Роли процесса», вверху, до таблицы ролей.
- Реестр [vdp/scripts/check-platform-mounts.sh](vdp/scripts/check-platform-mounts.sh) в том же diff перевести с `form-detail-page` на `process-roles-page`. Снять mount и оставить старую проверку нельзя (`fe-platform-mounts`).
- Тесты: [vdp/fe/src/lib/ved/manager-route-hint.test.ts](vdp/fe/src/lib/ved/manager-route-hint.test.ts) и [vdp/fe/e2e/manager-route-hint.spec.ts](vdp/fe/e2e/manager-route-hint.spec.ts) — менеджер на карточке не видит подсказку; root видит её на «Роли процесса».

Копирайт рычагов не переписывать. Статусную машину не трогать.

## Пункт 3. «Проверен» не нажимать, если уже проверен

В «Проверке участников сделки» у «ООО Пример» бейдж уже «Проверен», а зелёная кнопка «Проверен» всё равно открывает модалку «Одобрить участника». Повтор ничего не меняет.

Кнопки в [vdp/fe/src/components/ved/SubjectReview.tsx](vdp/fe/src/components/ved/SubjectReview.tsx) рисуются все три, без сверки со `subject.status`. Соответствие: `approved` → «Проверен», `waiting_verification` → «Запросить сведения», `blocked` → «Заблокировать». Статус `not_approved` («Не проверен») ни одной кнопке не равен — «Проверен» остаётся доступным.

Как должно быть:

- Кнопка текущего статуса не открывает модалку. Недоступна, с короткой причиной («Уже проверен» / «Сведения уже запрошены» / «Уже заблокирован»).
- Остальные переходы остаются. Это не смена матрицы заявки и не AuthZ: кто может проверять участников, не меняется.

Unit: при `approved` клик по «Проверен» не ставит `pending`. E2E на этот жест не обязателен, если unit покрывает запрет.

## Пункт 4. «Подтвердить» должно ставить «Проверен»

На контрагенте «Test reel» бейдж «Не проверен». Модалка «Одобрить участника» после «Подтвердить» закрывается, статус не меняется.

Почему. [SubjectReview.tsx](vdp/fe/src/components/ved/SubjectReview.tsx) вызывает `saveRefRecord` и сразу закрывает окно, не дожидаясь ответа и не показывая ошибку. Для контрагента запись одобрения в [platform-store.ts](vdp/fe/src/lib/ved/platform-store.ts) идёт только у комплаенса и root (`canSetApproval`). Менеджер, которому карточка кнопки уже показывает (`canReviewSubjects`), уходит в обычное обновление справочника без статуса. В ядре [SetCounterpartyApproval](vdp/core/internal/service/docs.go) менеджера тоже нет: только комплаенс и root. Одобрение организации ещё уже — только внутренний комплаенс.

Как должно быть:

- «Подтвердить» ждёт ответ. Успех — бейдж «Проверен» без перезагрузки страницы. Ошибка — текст в модалке, окно не закрывается молча.
- Кто видит кнопки проверки участников на карточке (комплаенс, менеджер, root), тот и может записать «Проверен». User и provider по-прежнему не могут. Та же роль на одобрении организации, иначе у менеджера сломается и «ООО Пример».
- Это не смена статуса заявки. Матрица «Подтвердить заявку» не трогается.

Тесты: FE — менеджерский вызов идёт в approval, а не в пустой patch; ошибка не глотается. Go — менеджер может поставить approval контрагенту и одобрить организацию; user — нет.

## Пункт 5. После «взять в проверку» — фокус на следующем шаге

Сейчас «Следующий шаг» — одна фраза («Подтвердить заявку»), а кнопки живут ниже в «Доступных действиях». После «Взять заявку в проверку» меняется только этот нижний список. Менеджер не видит, с чего продолжить.

Как должно быть на статусе, куда приводит «взять в проверку» (`form_verification`, и зеркально `organization_verification`):

- Блок «Следующий шаг» становится рабочей зоной: основной CTA («Подтвердить заявку») и короткие факты для решения — сумма, направление, контрагент, условие оплаты. Не дублировать всю карточку.
- «Доступные действия» остаются для вторичных: вернуть, приостановить, отклонить. Основную кнопку туда не копировать.
- До нажатия «взять в проверку» раскладка может остаться как сейчас. Смена видна сразу после перехода статуса.
- Статусы и набор действий не меняются. Меняется только место основной кнопки и факты рядом с ней.

Файлы: [form-detail-page.tsx](vdp/fe/src/components/ved/pages/form-detail-page.tsx) и [ActionPanel.tsx](vdp/fe/src/components/ved/ActionPanel.tsx). `ActionPanel` входит в path-filter pilot-matrix.

## Пункт 6. Красный «Возврат на доработку» клиенту здесь не нужен

У клиента на заявке `ВЭД-56291dfb` статус «Ожидает проверки менеджером». Справа уже сказано: действует менеджер, клиенту действий нет. Посередине красный блок «Возврат на доработку» с текстом `extraction_started`. Это не возврат и не просьба что-то исправить.

Откуда. Баннер в [form-detail-page.tsx](vdp/fe/src/components/ved/pages/form-detail-page.tsx) рисуется при любом `rejectText`. Текст берёт [rejectFromHistory](vdp/fe/src/lib/api/mappers.ts): последняя запись истории, у которой статус содержит `correction`. Старт распознавания пишет в историю комментарий `extraction_started` при том же статусе ([extraction_confirm.go](vdp/core/internal/service/extraction_confirm.go)). Если тогда заявка была на доработке, комментарий навсегда становится «причиной возврата» — даже после повторной отправки менеджеру.

Как должно быть:

- Клиент видит красный возврат только пока заявка реально на доработке (статус с `correction`) и есть человеческая причина.
- На «ожидает проверки менеджером» баннера нет.
- Служебные комментарии (`extraction_started`, `extraction_confirmed`) не считать причиной возврата и не показывать как текст алерта.

Подсказка «что исправить» на настоящей доработке остаётся. Статус заявки не меняется.

Unit: история с `extraction_started` на correction-статусе не даёт баннер на `form_waiting_verification`; настоящий комментарий возврата на статусе доработки — да.

## Пункт 7. Распознавание и параметры заявки расходятся

Окно «Распознанные данные» и блок «Параметры заявки» на одной заявке `ВЭД-56291dfb` показывают разное.

**1. Данные расходятся.** В окне сумма в шапке `1000 USD`, в строке позиции — `123000` при количестве `100` и цене `345` (это не `100 × 345`). После подтверждения в параметрах сумма `1 000,00 USD` — только шапка, строка нигде не сведена. Поле «Инвойс» в параметрах показывает `OCR-…`, а в окне это номер договора; номер инвойса там `INV-…`. Подтверждение в [extraction_confirm.go](vdp/core/internal/service/extraction_confirm.go) пишет в заявку сумму и валюту шапки и `contract_number`. Карточка берёт «Инвойс» из `contract_number` ([mappers.ts](vdp/fe/src/lib/api/mappers.ts), строка `invoiceNumber`).

Как должно быть:

- В окне, если сумма шапки не равна сумме строк или количество × цена не равно сумме строки, это видно до подтверждения. Нельзя молча оставить две суммы.
- В параметры попадает одна сумма — та, которую человек оставил в шапке после сверки.
- «Инвойс» в параметрах — номер инвойса (`INV-…`). Номер договора, если показываем, подписать «Договор», не «Инвойс».
- Статус заявки по-прежнему не меняется подтверждением распознавания.

**2. Код ТН ВЭД не выводится, хотя он есть.** В окне код `847130` и в шапке, и в строке. В параметрах — «—». Карточка читает только верхний ключ `invoice_json.hs_codes` (`hsCodeFromInvoiceJson`). Подтверждение сохраняет результат распознавания целиком: код лежит в `header.hs_codes`, верхнего ключа нет. `AttachHsCodes` этот верхний ключ пишет, подтверждение — нет.

Как должно быть: после подтверждения в «Код ТН ВЭД» виден `847130` (несколько кодов — через запятую, не прочерк). Читать и шапку распознавания, и верхний `hs_codes`, чтобы не потерять код, прикреплённый справочником.

Тесты: маппер на JSON распознавания с `header.hs_codes` отдаёт код, не «—»; «Инвойс» ≠ номер договора; подтверждение сохраняет код так, что карточка его видит.

## Пункт 8. Менеджеру ясно, что проверить, а не только «взять»

На статусе «ожидает проверки» блок «Следующий шаг» пишет «Взять заявку в проверку» — это подпись кнопки из [nextStepHint](vdp/fe/src/lib/api/mappers.ts). Само действие [eco_start](vdp/core/internal/service/form_payment.go) только меняет статус. Оно не говорит, какой документ открыть и какие поля сверить. Менеджер не понимает, смотреть инвойс, договор или что-то ещё.

Как должно быть в «Следующем шаге» до нажатия, по фактам этой заявки, не общим текстом:

- Какие документы открыть: инвойс и агентский договор из списка «Документы», по именам файлов.
- Что не сходится или пусто: код ТН ВЭД «—», контрагент «Не проверен». Если сумма шапки и строк расходится — это тоже пункт сверки (пункт 7).
- Что делает кнопка: фиксирует, что менеджер взял заявку. После неё решение — подтвердить или вернуть. Кнопка сама документы не проверяет.

Не выдумывать шаги, которых нет в статусе. Не менять матрицу действий.

## Пункт 9. В «Участниках» менеджер уже есть

После «взята в проверку» и «подтверждена» хронология показывает, что менеджер работает. В блоке «Участники» строка «Назначенный менеджер: не назначен».

Подпись берётся из `form.managerId` в [form-detail-page.tsx](vdp/fe/src/components/ved/pages/form-detail-page.tsx). Идентификатор пишется в [Transition](vdp/core/internal/service/form_payment.go) только если менеджер закрывает выключенный слот комплаенса и поле ещё пустое. Обычные «взять» и «подтвердить» его не ставят. Если идентификатор есть, а имени в списке учёток нет, интерфейс тоже пишет «не назначен».

Как должно быть: как только менеджер взял заявку или подтвердил её, в «Участниках» его имя. Запись `manager_id` на этих переходах, не только на выключенном слоте. Имя из учётки; нет имени — не подменять фразой «не назначен», если переход уже был.

## Пункт 10. «Клиент» — не суперадмин

В реестре заявок у суперадмина в колонке «Клиент» у обеих строк «Root Admin». Суперадмин не клиент. Клиент — участник с ролью «Клиент», учётка `user@` (в сиде `user@vdp.local`).

Откуда. Список заявок в [platform-store.ts](vdp/fe/src/lib/ved/platform-store.ts) всем заявкам подставляет `auth.displayName` — имя того, кто вошёл. Карточка заявки делает то же: [form-detail-page.tsx](vdp/fe/src/components/ved/pages/form-detail-page.tsx) передаёт `auth.displayName` в `mapCoreFormToPaymentForm`. Поэтому у менеджера в «Участниках» клиент был «Manager Seed». У заявки уже есть `account_id` владельца ([forms.ts](vdp/fe/src/lib/api/forms.ts)).

Как должно быть: «Клиент» — имя учётки с ролью клиента, которая создала заявку (`account_id`). Не root, не менеджер, не провайдер. Если имя не найдено — не подставлять текущего пользователя.

## Пункт 11. Окно «Распознанные данные»

**1. Вёрстка.** Поля правой колонки и таблица позиций вылезают за белую рамку модалки. Таблица в [ExtractionReviewPanel.tsx](vdp/fe/src/components/ved/ExtractionReviewPanel.tsx) задаёт `min-w-[44rem]`, а [Modal.tsx](vdp/fe/src/components/ved/Modal.tsx) не обрезает содержимое. Поля и таблица остаются внутри окна; широкая таблица листается внутри, а не раздвигает рамку.

**2. Валюта и ТН ВЭД — из справочника.** Сейчас оба поля — свободный ввод. Валюту выбирать из справочника валют, код ТН ВЭД — из справочника кодов, как в правке параметров заявки. В строке позиции то же. Свободный набор кода и валюты убрать. Если распознанного кода нет в справочнике — показать его и попросить выбрать ближайший из списка, не терять молча.

**3. Что распознано, а что вбито руками.** Все поля выглядят одинаково. При открытии запомнить исход распознавания. Поле без правки пометить «распознано». Поле, которое человек изменил, — «изменено». Легенда на видном месте, не только цветом. Низкая уверенность строки остаётся, но не заменяет эту подпись.

Статус заявки подтверждение по-прежнему не меняет. Сверка сумм — пункт 7, сюда не дублировать.

## Пункт 12. Шкала и следующий шаг — как рабочий статус

Обе заявки уже в рабочих статусах. Это видно в «Последних обновлениях» и в шапке карточки. Шкала «Жизненный цикл» и блок «Следующий шаг» этого не отражают: обе выглядят как «Проверка» и «дождитесь».

- `ВЭД-56291dfb`: список «Подтверждена», шапка «Заявка подтверждена менеджером». Шкала всё ещё на «Проверка», потому что у `form_accepted` этап `form_verification` в [statuses.ts](vdp/fe/src/lib/ved/statuses.ts). Клиенту следующий шаг — «действует менеджер, ждите», без того, что подтверждение уже есть и дальше договор. Красный «Возврат на доработку» здесь — пункт 6.
- `ВЭД-0eefb6e6`: список «У менеджера», шапка «Ожидает проверки организации менеджером». Это не черновик. Проверка организации схлопывается в ту же «Проверку» ([displayStageId](vdp/fe/src/lib/ved/process-stage-filters.ts)). Клиенту снова общее «ждите», хотя документов нет и ход у менеджера по организации.

Как должно быть: шкала и «Следующий шаг» совпадают со статусом из шапки. Подтверждённая заявка не стоит на «Проверке» — текущий этап «Договор», клиенту сказано, что менеджер назначает агента и договор, а не что заявка ещё на проверке. Ожидание проверки организации — отдельный шаг «организация», не та же «Проверка заявки». Коды статусов в домене не переименовывать.

## Пункт 13. Виджет «Участники» у менеджера — имена, не билиберда

Менеджер только что назначил провайдера. В «Участниках» три неверные строки:

- Клиент: «Manager Seed» — имя вошедшего менеджера, не владельца заявки. Это пункт 10.
- Назначенный менеджер: «не назначен», хотя по хронологии менеджер уже ведёт заявку. Это пункт 9.
- Провайдер: `55555555-5555-5555-5555-555555555555`. Это идентификатор учётки провайдера из сида, не имя. В [mappers.ts](vdp/fe/src/lib/api/mappers.ts) `providerName` копируется из `provider_id`. На карточке имя ищут в списке учёток, не находят и показывают этот идентификатор ([form-detail-page.tsx](vdp/fe/src/components/ved/pages/form-detail-page.tsx)).

Как должно быть в трёх строках: имя клиента с ролью «Клиент», имя менеджера, который ведёт заявку, имя провайдера. Идентификатор в подписи не показывать. Нет имени — «не назначен», а не UUID.

В той же хронологии после назначения виден служебный комментарий `resolve_contract_branch` ([contract.go](vdp/core/internal/service/contract.go)). В ленте человеку — «ожидает подписанный агентский договор», без имени внутренней функции.

## Пункт 14. «Участники» — одно и то же у всех ролей, без прочерков

Одна и та же заявка. У суперадмина: клиент «Ivan Petrov», менеджер «Manager Seed», провайдер «не назначен». У другой роли: «Клиент не найден», «имя не найдено», «не назначен». Виджет врёт не потому, что людей нет, а потому что имена ищутся в списке учёток.

Откуда. Подписи в [form-detail-page.tsx](vdp/fe/src/components/ved/pages/form-detail-page.tsx) считают `resolveClientName`, `assignedManagerLabel`, `assignedProviderLabel` из [mappers.ts](vdp/fe/src/lib/api/mappers.ts). Список учёток — `GET /api/v1/admin/account`, запрос включён только для root и менеджера, а сам список в ядре только у root. Суперадмин находит имена. Остальные получают пустой список: клиент становится «не найден», назначенный менеджер — «имя не найдено». Провайдер без id у обеих ролей честно «не назначен».

Как должно быть:

- Кто видит карточку заявки, видит одни и те же три строки. Не зависит от того, может ли роль открыть справочник учёток.
- Есть человек — его имя. Нет назначения — статус, по которому понятно, что делать («не назначен»). Не прочерк, не UUID, не «не найден», если запись в системе есть.
- «Клиент не найден» и «имя не найдено» — только если идентификатор есть, а имени в данных заявки действительно нет. Не как замена закрытого списка учёток.
- Имена приходят с проекцией заявки (владелец, менеджер, провайдер: id и отображаемое имя). Полный список учёток с почтой и прочими полями другим ролям не открывать.

Подпункт к правкам карточки: пустое поле не рисуется чертой. Либо значение, либо короткая фраза-статус. Это уже сделано для реквизитов в пункте 1; для «Участников» тот же принцип, и фраза должна быть правдой для всех ролей.

Тесты: одна заявка с клиентом и менеджером — root и роль без списка учёток получают те же подписи; провайдер без id — «не назначен», не «—» и не UUID.
