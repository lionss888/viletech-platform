# Этап 0: Граница возврата после исполнения

## Цель

Зафиксировать **до первой строки кода**, что пилотный refund и новый контур не смешиваются. Записать инварианты, границы, что вне scope.

## Контекст

В VDP уже есть возврат удержанных средств (Phase 7):
- [`vdp/docs/domain/form-lifecycle.md`](vdp/docs/domain/form-lifecycle.md) §Ветка refund
- [`vdp/core/internal/domain/formpayment/refund.go`](vdp/core/internal/domain/formpayment/refund.go): `mgr_refund_init/start/stop/sent/cancel`
- Поля `FundsHeld`, `FundsRefunded`
- Инвариант: отмена заявки блокируется при `FundsHeld && !FundsRefunded`
- Казначей в матрице
- E2E [`vdp/fe/e2e/pilot-matrix-refund.spec.ts`](vdp/fe/e2e/pilot-matrix-refund.spec.ts)

Заказчик прислал новый процесс ([`вводные/Процесс возврата.txt`](вводные/Процесс возврата.txt)): деньги уже ушли и вернулись на счёт провайдера.

## Два возврата (не смешивать)

### Пилотный refund (Phase 7)

| Что | Значение |
|---|---|
| Инициатор | Менеджер |
| Когда | До/вокруг исполнения; удержанные средства ещё у менеджера |
| Статусы | `payment_refund_waiting`, `payment_refund_processing`, `payment_refund_sent` |
| Действия | `mgr_refund_init/start/stop/sent/cancel` |
| Поля | `FundsHeld`, `FundsRefunded` |
| Роли | Менеджер, казначер |
| Инвариант | Нельзя cancel заявку при `FundsHeld && !FundsRefunded` |
| Покрытие | Домен, HTTP, FE, E2E `pilot-matrix-refund.spec.ts` |

**Не трогаем.** Phase 7 остаётся как есть.

### Новый контур (после исполнения)

| Что | Значение |
|---|---|
| Инициатор | Провайдер |
| Когда | После исполнения (`payment_sent` и далее, включая `report_accepted`/`completed`); деньги вернулись на счёт провайдера |
| Статусы | Новые (рабочие имена в §Naming) |
| Действия | Новый префикс, например `prov_return_*`, `mgr_return_*`, `client_return_*` |
| Поля | Новые (не `FundsHeld`/`FundsRefunded`) |
| Роли | Провайдер (сообщает), менеджер (выбирает ветку), клиент (отвечает) |
| Казначер | Не участвует |
| Инварианты | См. §Инварианты ниже |

**Не использовать:** `mgr_refund_*`, `payment_refund_*`, `FundsHeld`, `FundsRefunded`.

**Не переиспользовать:** `prov_payment_return` (тот уводит в `manager_checking` — другая семантика).

## Инварианты нового контура

1. **Один активный возврат** на заявку. Второй старт, пока эпизод не закрыт, — явная ошибка политики.
2. **Только импорт:** `DirectionImport`. Экспорт — отказ.
3. **Аванс и постоплата:** оба входят. `rate_on_provider_postpay` overlay не исключает.
4. **Вход после исполнения:** провайдер может сообщить с момента, когда приложил платёжный документ и нажал «Исполнить платёж». В том числе после подписанного акта (`report_accepted`, `completed`).
5. **Сумма неизменяема:** задаёт провайдер; менеджер и клиент не правят.
6. **Частичный — не отдельная ветка:** если сумма неполная, менеджер разбирает с клиентом вручную; дальше те же три решения.
7. **Клиент не инициирует:** не может начать возврат, не выбирает ветку, не меняет сумму провайдера.
8. **Казначер не участвует** в новом контуре (в отличие от пилотного refund).
9. **Письмо-согласие остаётся:** клиент прикладывает при согласии на курс; без письма выплата невозможна.
10. **Подтверждение получения рублей снято:** менеджер приложил рублёвую платёжку = эпизод «вернуть клиенту» закрыт.
11. **Повтор платежа — без новой заявки:** документы, комплаенс, исходная оплата клиента не повторяются.
12. **Контрагент не проверяется заново** при повторе (даже если сменили организацию провайдера).
13. **Идемпотентность:** повтор команды провайдера «сообщить о возврате» с теми же параметрами не создаёт второй эпизод.

## Что вне scope (для всех этапов 0-5)

- **Экспорт**
- **Казначер** в новом контуре (остаётся в пилотном refund)
- **Новая заявка** при повторе платежа
- **Роль «суперадмин»** в кабинете (внутренний доступ есть, кабинетную роль не заводим)
- **Учёт остатка** при частичной сумме (нет поля «остаток»; менеджер разбирает вручную)
- **Подтверждение «клиент получил рубли»** (сняли по ответу заказчика)
- **Повторная проверка контрагента** при повторе исполнения
- **ML / FaaS / serverless** (событийные side-paths не планируем на MVP)
- **Смена статусов через фоновую функцию** (только явные команды ролей)
- **Замена пилотного refund** (два контура живут параллельно)
- **`release-gate`** (только `ci-pr-pilot` в DoD каждого этапа)
- **Уведомление менеджмента** до закрытия волны (только после зелёного gate последнего этапа)
- **Тихий `compose-fe-refresh`** (спрашивать перед обновлением deps)

## Naming (рабочие имена)

Префиксы действий и статусов. Точные имена определятся в этапе 1 при реализации домена.

### Статусы (примеры)

- `prov_return_reported` или `return_reported` — провайдер сообщил факт
- `mgr_return_decision` или `return_awaiting_mgr_decision` — менеджер выбирает ветку
- `mgr_return_clarify_client` — уточнение у клиента
- `client_return_clarify_response` — клиент ответил
- `mgr_return_to_client_rate` — менеджер выставил курс
- `client_return_consent_pending` — клиент рассматривает
- `client_return_consent_given` — клиент приложил письмо
- `mgr_return_to_client_sent` — менеджер выплатил рубли
- `mgr_return_repeat_initiated` — менеджер выбрал повтор
- `prov_return_repeat_executing` — провайдер исполняет повтор
- `return_episode_closed` — эпизод закрыт

### Действия (примеры)

- `prov_return_report` — провайдер: сообщить о возврате
- `mgr_return_clarify` — менеджер: уточнить у клиента
- `client_return_clarify_reply` — клиент: ответить на уточнение
- `mgr_return_to_client` — менеджер: вернуть клиенту (выставить курс)
- `client_return_consent` — клиент: приложить письмо-согласие
- `client_return_refuse` — клиент: отказать
- `mgr_return_to_client_execute` — менеджер: выплатить рубли
- `mgr_return_repeat` — менеджер: повторить платёж
- `prov_return_repeat_execute` — провайдер: исполнить повтор

**Не использовать:** `mgr_refund_*`, `prov_payment_return`.
