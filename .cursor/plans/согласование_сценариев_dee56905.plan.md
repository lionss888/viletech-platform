# Согласование сценариев по ролям

## Цель

Артефакт для согласования с менеджментом заказчика: **простые текстовые описания** «как идёт заявка» глазами четырёх ролей. Не код, не UI, не автотесты.

Стиль — как в согласованных примерах: короткий абзац «кто → что делает → итог», без жаргона id/статусов в заголовке; машинный id сценария — мелкой пометкой в конце блока для связки с роботами.

## Куда кладём

Папка (создать):

[`заметки/согласование сценариев/`](заметки/согласование%20сценариев/)

Файлы:

- [`оглавление.txt`](заметки/согласование%20сценариев/оглавление.txt) — зачем папка, для кого, как читать, соответствие канону [`vdp/docs/pilot/scenario-role-directory.md`](vdp/docs/pilot/scenario-role-directory.md)
- [`клиент.txt`](заметки/согласование%20сценариев/клиент.txt)
- [`менеджер.txt`](заметки/согласование%20сценариев/менеджер.txt)
- [`провайдер.txt`](заметки/согласование%20сценариев/провайдер.txt)
- [`казначей.txt`](заметки/согласование%20сценариев/казначей.txt)

Формат: обычный текст (как другие заметки в `заметки/`), UTF-8, без rich markdown-таблиц.

## Объём (зафиксировано)

Не «по 1–2 на роль», а **полный набор для согласования пилота**:

1. **Spine приёмки (6)** — обязательно во всех релевантных ролях (один сквозной рассказ + что делает эта роль).
2. **Остальные сценарии каталога (17)**, где роль участвует или видит исход.
3. **Расширение:** `happy_path_shipment_branch`.
4. **Денежные лестницы** (для казначея и менеджера): advance, postpay RATE_ON_PP, export PAY_FROM_EXPORT, refund, shipment.

Вне текста для менеджмента (только упоминание в оглавлении «не роль процесса»): root cancel, health_core. Bank channel — коротко в блоке клиента/менеджера как «заявка пришла из банка».

Пилотный контекст в оглавлении одной фразой: ICO/ECO по умолчанию выключены, шаги комплаенса закрывает менеджер (continuity).

## Шаблон одного маршрута (одинаковый везде)

```
Название (человеческое)
Кто участвует: …
Как проходит: … (3–6 предложений, как в примерах)
Итог: …
Пометка для команды: id=… (каталог / ladder)
```

## Содержание по ролям

### Клиент
Маршруты, где клиент действует или явно ждёт:
- полный путь до закрытия (свой кусок: создать, документы, отправить, отчёт/подтверждения)
- возврат на доработку и повторная подача
- проверка организации (если орг. ещё не одобрена — что видит клиент)
- подтверждение OCR / сумма
- заявка от банка (клиент может не сидеть в кабинете ВЭД — что меняется)
- отгрузка (если включена ветка): загрузка закрывающих документов

### Менеджер
- continuity: принять заявку без ECO
- вернуть на коррекцию
- приём оплаты и назначение провайдера
- курс сделки
- не видит черновики клиента
- просмотр документа
- возврат провайдера менеджеру
- полный путь до закрытия (координация)
- refund / отмена при незавершённом возврате
- денежные лестницы: где менеджер vs казначей
- отгрузка: старт/стоп/accept со стороны менеджера
- метка Bank API на заявке

### Провайдер
- карточка без ПДн клиента
- исполнить и подтвердить платёж
- вернуть платёж менеджеру
- свой участок на полном пути и на postpay/advance (без лишних полей клиента)

### Казначей
Отдельный файл — фокус на платёжных режимах (источник: [`e2e-coverage-matrix.md`](vdp/docs/development/e2e-coverage-matrix.md) journeys IMP/export):
- импорт advance + срок исполнения
- импорт postpay RATE_ON_PP (курс/комиссия после ПП)
- экспорт PAY_FROM_EXPORT
- что казначей **не** делает (не комплаенс, не ПДн провайдеру)

Перекрёстные ссылки: один и тот же id может повторяться в 2–3 файлах с **разным углом** («что делаю я»), без копипасты полного абзаца чужой роли.

## Порядок работ

1. Создать папку и `оглавление.txt` (правила чтения + пилот continuity + список файлов).
2. Написать `менеджер.txt` и `клиент.txt` первыми (spine + возврат) — быстрая сверка тона с вами при необходимости.
3. Дописать `провайдер.txt` и `казначей.txt` (лестницы).
4. Пройти чеклист полноты: каждый id из каталога 17 + shipment + 5 ladder упомянут хотя бы в одном файле или явно вынесен в «служебное» в оглавлении.
5. Короткая сверка формулировок со справочником (названия ролей: Клиент / Менеджер / Провайдер / Казначей; без DoD-жаргона в тексте для менеджмента).
