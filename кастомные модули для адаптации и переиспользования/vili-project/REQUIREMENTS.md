# Требования к системе Вили (VILI)

## Обзор

Данный документ описывает функциональные и нефункциональные требования к системе Вили, а также детальное описание функциональности.

**Дата создания:** 2025-01-27  
**Версия:** 1.0

---

## Бизнес-требования

### Цель проекта

Создать AI-ассистент для автоматизации документооборота международных платежей (традиционных и криптовалютных), который:

1. **Сокращает время обработки платежей** — автоматизация рутинных операций
2. **Повышает точность compliance-проверок** — использование AI для анализа
3. **Снижает операционные затраты** — эффективная обработка документов
4. **Адаптивно обучается** — улучшение на основе обратной связи операционистов
5. **Работает вместе со специалистом** — помощь, а не замена операциониста
6. **Улучшает коммуникацию с клиентами** — операционист фокусируется на клиенте

### Целевая аудитория

- **Операционисты** — основные пользователи системы
- **Специалисты по compliance** — использование для проверок
- **Финансовые специалисты** — анализ и валидация платежей
- **Менеджеры по документам** — управление документооборотом

### Бизнес-ценность

- **Эффективность:** Сокращение времени обработки платежей на 50%+
- **Точность:** Повышение точности compliance-проверок на 20%+
- **Затраты:** Снижение операционных затрат на 30%+
- **Качество:** Улучшение качества обслуживания клиентов

## Функциональные требования

### FR-1: Анализ документов платежей

#### FR-1.1: Поддержка форматов документов

**Требование:** Система должна поддерживать следующие форматы документов:

- **SWIFT сообщения:**
  - MT103 (Customer Credit Transfer)
  - MT202 (General Financial Institution Transfer)
  - Другие стандартные SWIFT форматы

- **Документы:**
  - PDF документы
  - XML файлы
  - JSON данные
  - Текстовые файлы

**Описание:** Система должна автоматически определять формат документа и применять соответствующий парсер.

**Критерии приемки:**
- ✅ Система корректно распознает формат документа
- ✅ Парсинг выполняется без ошибок
- ✅ Извлеченные данные валидируются

#### FR-1.2: Извлечение данных из документов

**Требование:** Система должна извлекать следующие данные:

- **Базовые данные:**
  - Сумма платежа
  - Валюта
  - Дата платежа
  - Отправитель (отправители)
  - Получатель (получатели)
  - Назначение платежа

- **Дополнительные данные:**
  - Номера счетов
  - Банковские реквизиты
  - Референсы транзакций
  - Комментарии и примечания

**Описание:** Использование FinGPT для извлечения структурированных данных из неструктурированных документов.

**Критерии приемки:**
- ✅ Точность извлечения данных > 95%
- ✅ Все обязательные поля извлекаются
- ✅ Данные валидируются на корректность

#### FR-1.3: Анализ тональности документов

**Требование:** Система должна анализировать тональность документов для выявления:

- Негативных индикаторов
- Рисковых формулировок
- Подозрительных паттернов в тексте

**Описание:** Использование FinGPT v3.3 для анализа настроений в документах.

**Критерии приемки:**
- ✅ Система корректно определяет тональность
- ✅ Рисковые формулировки выявляются
- ✅ Результаты используются в оценке рисков

---

### FR-2: Compliance проверки

#### FR-2.1: Sanctions Screening

**Требование:** Система должна проверять участников платежа против санкционных списков:

- OFAC (Office of Foreign Assets Control)
- EU Sanctions
- UN Sanctions
- Локальные санкционные списки

**Описание:** Автоматическая проверка всех участников платежа против актуальных санкционных списков.

**Критерии приемки:**
- ✅ Все участники проверяются против списков
- ✅ Результаты проверки отображаются операционисту
- ✅ Обновление списков происходит автоматически

#### FR-2.2: AML/KYC проверки

**Требование:** Система должна выполнять AML/KYC проверки:

- Проверка KYC документов клиентов
- Анализ AML паттернов
- Выявление подозрительных транзакций
- Проверка PEP (Politically Exposed Persons)

**Описание:** Автоматическая проверка соответствия AML/KYC требованиям.

**Критерии приемки:**
- ✅ KYC документы проверяются автоматически
- ✅ AML паттерны выявляются
- ✅ Результаты проверки документируются

#### FR-2.3: Travel Rule (для крипто)

**Требование:** Для криптовалютных платежей система должна:

- Проверять соответствие Travel Rule требованиям
- Валидировать данные отправителя и получателя
- Генерировать Travel Rule отчеты
- Обеспечивать соответствие FATF рекомендациям

**Описание:** Автоматическая проверка Travel Rule для криптовалютных транзакций выше порога.

**Критерии приемки:**
- ✅ Travel Rule проверяется для транзакций > $1000
- ✅ Данные отправителя/получателя валидируются
- ✅ Отчеты генерируются автоматически

### FR-3: Оценка рисков

#### FR-3.1: Оценка рисков платежей

**Требование:** Система должна оценивать риски платежей на основе:

- Анализа документов
- Compliance проверок
- Экономических индексов стран
- Исторических данных
- Паттернов транзакций

**Описание:** Использование FinRL для оценки рисков с адаптивным обучением.

**Критерии приемки:**
- ✅ Risk score генерируется для каждого платежа
- ✅ Риски классифицируются (low/medium/high/critical)
- ✅ Рекомендации генерируются на основе рисков

#### FR-3.2: Экономическая оценка рисков

**Требование:** Система должна использовать экономические индексы для оценки рисков:

- Индекс экономической свободы
- Индекс восприятия коррупции
- Индекс ведения бизнеса
- Индекс глобализации
- Макроэкономические показатели

**Описание:** Интеграция экономических индексов в оценку рисков платежей.

**Критерии приемки:**
- ✅ Экономические индексы учитываются в оценке рисков
- ✅ Данные индексов актуальны
- ✅ Индексы используются для адаптации порогов риска

#### FR-3.3: Выявление паттернов отмывания (для крипто)

**Требование:** Для криптовалютных платежей система должна выявлять:

- Структурирование (structuring)
- Mixing/tumbling сервисы
- Peppercorning
- Быстрое движение средств через множество кошельков
- Связи с санкционными адресами

**Описание:** Использование FinRL для выявления паттернов отмывания в блокчейне.

**Критерии приемки:**
- ✅ Паттерны отмывания выявляются автоматически
- ✅ Подозрительные транзакции помечаются
- ✅ SAR отчеты генерируются при необходимости

## Нефункциональные требования

### NFR-1: Производительность

#### NFR-1.1: Время обработки

**Требование:**
- Базовый анализ документа: < 30 секунд
- Расширенный анализ: < 2 минуты
- API latency (p95): < 500ms

**Описание:** Система должна обрабатывать документы быстро для эффективной работы операционистов.

#### NFR-1.2: Throughput

**Требование:**
- Обработка документов: > 100 документов/час на инстанс
- Масштабируемость: горизонтальное масштабирование

**Описание:** Система должна обрабатывать большой объем документов.

#### NFR-1.3: Ресурсы

**Требование:**
- Эффективное использование GPU/CPU
- Оптимизация памяти
- Batch processing для эффективности

**Описание:** Оптимизация использования ресурсов для снижения затрат.
