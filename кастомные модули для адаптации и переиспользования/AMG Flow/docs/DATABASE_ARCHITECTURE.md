# 🗄️ Архитектура баз данных для аналитики

## 📋 Обзор

Документ описывает различные подходы к организации баз данных для системы аналитики AMG Flow и рекомендации по выбору оптимального решения.

## 🎯 Варианты архитектуры

### 1. **Единая база данных** (Текущий подход)

```
┌─────────────────────────────────┐
│        PostgreSQL               │
│  ┌─────────────┐ ┌─────────────┐│
│  │   Messages  │ │  Analytics  ││
│  │   (Chat)    │ │  (Tracking) ││
│  └─────────────┘ └─────────────┘│
└─────────────────────────────────┘
```

**✅ Преимущества:**
- **Простота развертывания** - одна база данных
- **ACID транзакции** - целостность данных
- **Простые запросы** - JOIN между таблицами
- **Единая точка управления** - один сервер
- **Низкие требования** - меньше ресурсов

**❌ Недостатки:**
- **Конфликт нагрузок** - OLTP vs OLAP
- **Сложность масштабирования** - вертикальное только
- **Риск блокировок** - аналитика блокирует операции
- **Сложность оптимизации** - разные индексы

**💡 Когда использовать:**
- Небольшие объемы данных (< 1M записей/день)
- Простые аналитические запросы
- Ограниченные ресурсы
- Быстрый старт проекта

### 2. **Отдельная аналитическая база**

```
┌─────────────────┐    ┌─────────────────┐
│   PostgreSQL    │    │   PostgreSQL    │
│   (Operational) │    │   (Analytics)   │
│                 │    │                 │
│  ┌─────────────┐│    │  ┌─────────────┐│
│  │   Messages  ││    │  │  Analytics  ││
│  │   (Chat)    ││    │  │  (Tracking) ││
│  └─────────────┘│    │  └─────────────┘│
└─────────────────┘    └─────────────────┘
```

**✅ Преимущества:**
- **Изоляция нагрузок** - независимые операции
- **Независимое масштабирование** - разные ресурсы
- **Оптимизация под аналитику** - специальные индексы
- **Безопасность данных** - раздельный доступ
- **Резервное копирование** - независимые бэкапы

**❌ Недостатки:**
- **Сложность синхронизации** - дублирование данных
- **Управление двумя базами** - больше операций
- **Сложность транзакций** - нет ACID между базами
- **Дополнительные ресурсы** - два сервера

**💡 Когда использовать:**
- Средние объемы данных (1M-10M записей/день)
- Сложные аналитические запросы
- Необходимость изоляции
- Планы масштабирования

### 3. **Специализированная аналитическая БД**

```
┌─────────────────┐    ┌─────────────────┐
│   PostgreSQL    │    │   ClickHouse    │
│   (Operational) │    │   (Analytics)   │
│                 │    │                 │
│  ┌─────────────┐│    │  ┌─────────────┐│
│  │   Messages  ││    │  │  Analytics  ││
│  │   (Chat)    ││    │  │  (Tracking) ││
│  └─────────────┘│    │  └─────────────┘│
└─────────────────┘    └─────────────────┘
```

**✅ Преимущества:**
- **Оптимальная производительность** - специализированные функции
- **Горизонтальное масштабирование** - кластеры
- **Сжатие данных** - экономия места
- **Параллельная обработка** - быстрые запросы
- **Временные ряды** - оптимизация для аналитики

**❌ Недостатки:**
- **Сложность инфраструктуры** - новые технологии
- **Высокие требования** - много ресурсов
- **Сложность синхронизации** - разные форматы
- **Обучение команды** - новые навыки

**💡 Когда использовать:**
- Большие объемы данных (> 10M записей/день)
- Сложная аналитика и ML
- Требования к производительности
- Длительные временные ряды

## 🎯 Рекомендации по выбору

### **Этап 1: Начало проекта** (0-6 месяцев)
**Рекомендация: Единая база + оптимизация**

```yaml
# docker-compose.yml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: appdb
    # Оптимизации для аналитики
    command: >
      postgres
      -c shared_preload_libraries=pg_stat_statements
      -c max_connections=200
      -c shared_buffers=256MB
      -c effective_cache_size=1GB
```

**Оптимизации:**
- Специальные индексы для аналитики
- Материализованные представления
- Партиционирование таблиц
- Политики хранения данных

### **Этап 2: Рост проекта** (6-18 месяцев)
**Рекомендация: Отдельная аналитическая база**

```yaml
# docker-compose.analytics.yml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: appdb
  analytics_db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: analytics
    # Оптимизации для аналитики
    command: >
      postgres
      -c shared_preload_libraries=pg_stat_statements
      -c max_connections=200
      -c shared_buffers=512MB
      -c effective_cache_size=2GB
```

**Преимущества:**
- Изоляция операционных и аналитических нагрузок
- Независимое масштабирование
- Специализированная оптимизация
- Безопасность данных

### **Этап 3: Масштабирование** (18+ месяцев)
**Рекомендация: Специализированная аналитическая БД**

```yaml
# docker-compose.analytics-advanced.yml
services:
  db:
    image: postgres:16-alpine
  analytics_db:
    image: clickhouse/clickhouse-server
    environment:
      CLICKHOUSE_DB: analytics
```

**Преимущества:**
- Оптимальная производительность для аналитики
- Горизонтальное масштабирование
- Сжатие данных
- Параллельная обработка

## 🛠️ План миграции

### **Миграция с единой БД на отдельную**

1. **Подготовка**
   ```bash
   # Создать резервную копию
   docker compose exec db pg_dump -U user -d appdb > backup.sql
   ```

2. **Создание аналитической БД**
   ```bash
   # Запустить с отдельной БД
   docker compose -f docker-compose.analytics.yml up -d
   ```

3. **Миграция данных**
   ```bash
   # Запустить скрипт миграции
   ./scripts/migrate_to_analytics_db.sh
   ```

4. **Тестирование**
   ```bash
   # Проверить работу системы
   make health
   make analytics-daily
   ```

### **Миграция на специализированную БД**

1. **Выбор технологии**
   - ClickHouse - для временных рядов
   - TimescaleDB - для PostgreSQL-совместимости
   - Apache Druid - для real-time аналитики

2. **Настройка синхронизации**
   - Kafka для стриминга данных
   - Debezium для CDC
   - Custom ETL процессы

3. **Оптимизация запросов**
   - Переписать запросы под новую БД
   - Настроить индексы и партиции
   - Оптимизировать агрегации

## 📈 Мониторинг производительности

### **Метрики для отслеживания**

```sql
-- Производительность запросов
SELECT 
    query,
    calls,
    total_time,
    mean_time,
    rows
FROM pg_stat_statements 
ORDER BY total_time DESC 
LIMIT 10;

-- Использование индексов
SELECT 
    schemaname,
    tablename,
    indexname,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes 
ORDER BY idx_scan DESC;

-- Размеры таблиц
SELECT 
    schemaname,
    tablename,
    pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) as size
FROM pg_tables 
WHERE schemaname = 'public'
ORDER BY pg_total_relation_size(schemaname||'.'||tablename) DESC;
```

### **Алерты и уведомления**

```yaml
# monitoring/alerts.yml
alerts:
  - name: "High Query Time"
    condition: "avg_query_time > 1000ms"
    action: "scale_database"
  
  - name: "Low Disk Space"
    condition: "disk_usage > 80%"
    action: "cleanup_old_data"
  
  - name: "High Connection Count"
    condition: "active_connections > 150"
    action: "scale_connection_pool"
```

## 🔒 Безопасность и соответствие

### **Разделение доступа**

```sql
-- Создать пользователей с разными правами
CREATE USER operational_user WITH PASSWORD 'operational_pass';
CREATE USER analytics_user WITH PASSWORD 'analytics_pass';

-- Права для операционной БД
GRANT SELECT, INSERT, UPDATE, DELETE ON messages TO operational_user;
GRANT USAGE ON SCHEMA public TO operational_user;

-- Права для аналитической БД
GRANT SELECT ON ALL TABLES IN SCHEMA public TO analytics_user;
GRANT USAGE ON SCHEMA public TO analytics_user;
```

```yaml
services:

      - ./certs:/certs:ro
```

## 📚 Заключение

**Для AMG Flow рекомендую:**

1. **Начать с единой БД** + оптимизации
2. **Мигрировать на отдельную БД** при росте нагрузки
3. **Рассмотреть специализированную БД** при больших объемах

**Критерии для миграции:**
- > 1M записей аналитики в день
- Запросы аналитики занимают > 30% времени БД
- Необходимость real-time аналитики
- Требования к горизонтальному масштабированию
