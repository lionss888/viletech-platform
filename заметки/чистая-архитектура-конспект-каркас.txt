================================================================================
0. ЗАЧЕМ ЭТО НАМ (ВЭД)
================================================================================

Цель архитектуры у Мартина (своими словами): отделить политику бизнеса от деталей
(фреймворк, БД, UI, провайдеры), чтобы бизнес-правила жили дольше и менялись дешевле.

Для платформы ВЭД это значит:
- статусы заявки и допустимые переходы ролей — политика (ядро);
- Nest/Go, Mongo, кабинеты BDUI, коннекторы провайдера — детали (края);
- UI не источник истины по статусу; REST/события — адаптеры к политике.

Связанные project rules:
- границы-и-контексты
- интеграция-и-события
- безопасность-ролей-и-данных
- устойчивость-и-наблюдаемость
- правила-построения

================================================================================
2. SOLID (кратко, своими словами) + ЧЕКЛИСТ ВЭД
================================================================================

S — Single Responsibility / одна причина менять.
  Заявка ≠ генерация PDF ≠ OCR ≠ коннектор банка.

O — Open/Closed: расширять поведение без правки ядра.
  Новый провайдер — новый адаптер, не правки машины статусов.

L — Liskov: подтипы не ломают контракт.
  «Провайдер A/B» за одним портом исполнения платежа.

I — Interface Segregation: узкие порты.
  Provider DTO без ПДн клиента; User не видит внутренние поля compliance.

D — Dependency Inversion: ядро зависит от абстракций, детали — от ядра.
  Use case «назначить провайдера» не импортирует HTTP-клиент RailsR/Striga.

Чеклист:
[ ] Переход статуса заявки живёт в домене / application, не в виджете кабинета
[ ] Роль проверяется на границе use case / endpoint, не только в UI
[ ] Коннектор провайдера за портом (interface), вызывается снаружи ядра
[ ] Recognition/OCR не на транзакционном пути смены статуса оплаты
[ ] Идемпотентность действий с деньгами — в контракте порта, не «надеемся на UI»

================================================================================
3. ПРАВИЛО ЗАВИСИМОСТЕЙ (Dependency Rule)
================================================================================

Стрелки зависимостей исходного кода направлены ВНУТРЬ:
  Frameworks & Drivers  →  Interface Adapters  →  Application (Use Cases)  →  Entities

Внутренние круги не знают о внешних. Имена, типы, фреймворки с края не протекают в ядро.

Слои (рабочие ярлыки):
1) Entities — неизменные бизнес-правила предприятия (заявка, статусы, роли как политика).
2) Use Cases — сценарии приложения (submit, approve internal CO, assign provider, execute payment…).
3) Interface Adapters — контроллеры, презентеры, gateways, маппинг DTO ↔ домен.
4) Frameworks & Drivers — Nest, HTTP, Mongo, очереди, UI, внешние API.

Humble Object: хрупкий край (UI, ORM) тонкий; тестируемая логика — рядом, но не смешана.

Чеклист ВЭД:
[ ] form-payment / lifecycle: статусы и матрица действий ролей не зависят от BDUI schema
[ ] bdui-клиент только рендерит схему; не «хранит» бизнес-статус как истину
[ ] Mongo-схемы / ORM-модели не торчат в use case как каноническая модель
[ ] События очереди несут бизнес-термины (id заявки, новый статус), не внутренности коннектора

================================================================================
4. ГРАНИЦЫ И BOUNDED CONTEXTS
================================================================================

Граница = место, где политика отделяется от детали и где можно поставить порт.

Разрез платформы (из rules, не из книги):
  auth/RBAC | заявка+статусы | compliance | documents | payments+connectors | company

Пока нет мотива независимого деплоя/масштаба/команды — модульный монолит с пакетами.
Не шарить БД при будущем разрезании. Не резать «все репозитории / все контроллеры».

Частичная граница: иногда достаточно пакетов + интерфейсов без отдельного процесса.
Полная граница: отдельный сервис, своя БД, явный контракт.

Чеклист:
[ ] Каждый новый модуль назван по бизнес-возможности, не по технике
[ ] ПДн клиента не пересекают границу к Provider
[ ] Платежный коннектор — деталь за портом payments
[ ] Есть план транзакционной границы заявки, если когда-нибудь разрежем сервис

================================================================================
5. USE CASES КАК ЦЕНТР СЦЕНАРИЕВ
================================================================================

Один use case ≈ одно намерение актора + вход/выход + допустимые статусы.

Примеры ВЭД (черновик карты):
  User: создать черновик, submit, закрыть/подтвердить получение
  Internal CO: approve / reject / request fixes (рос. орг.)
  External CO: review сделки / документов
  Manager: назначить провайдера, видеть очередь
  Provider: принять в работу, исполнить, подтвердить (платёжка/хеш)

Вход use case: команды + DTO на границе.
Выход: результат / новый статус / события для уведомлений и документов.
Ошибки политики (недопустимый переход, чужая роль) — явные, не 500 из ORM.

Чеклист (связать с lifecycle-планами P0–P7):
[ ] Каждое действие из матрицы ролей = именованный use case / action
[ ] Тест: допустимый переход + запрет чужой роли
[ ] Тест: идемпотентный повтор оплаты / подтверждения
[ ] Наблюдаемость: correlation id заявки сквозь use case → адаптер → лог

================================================================================
6. ДЕТАЛИ КАК ПЛАГИНЫ
================================================================================

БД, веб-фреймворк, UI, брокер — детали, которые «втыкаются» снаружи.
Архитектура должна позволять отложить или заменить деталь без переписывания политики.

Практично для нас:
- Сейчас: Nest + Mongo в fea — ок как деталь монолита.
- BDUI schema service — адаптер представления кабинетов, не домен заявки.
- fe-experiment lifecycle matrix — хорошее место держать политику действий отдельно от виджетов.

Не делать:
- «сначала выбрать ORM/очередь, потом придумать статусы»
- тащить StageHash / статусы только во frontend

================================================================================
7. ТЕСТИРОВАНИЕ И АРХИТЕКТУРА
================================================================================

Тесты ядра (entities + use cases) — быстрые, без Nest/Mongo/браузера.
Контрактные / consumer-driven — на межсервисные API, когда появятся.
E2E (Playwright) — критичные пути кабинетов, не единственная страховка домена.

Чеклист (правила-построения + nestjs-testing):
[ ] Unit на переходы статусов и матрицу ролей
[ ] Unit на порты провайдера (мок коннектора)
[ ] Нет публичных smoke вроде admin/test на проде
[ ] E2E только на ключевые флоу ролей, без хрупкого дублирования всей матрицы
