1. ЧТО ТРЕБУЕТ ДОКУМЕНТ (ЯДРО ПРОДУКТА)
================================================================================

Это не «общий банкинг», а платформа ВЭД-платежей с процессным ядром.

Роли:
- User — только свои заявки
- Internal compliance officer — проверка российских организаций (первая заявка)
- External compliance officer — проверка иностранных организаций / документов сделки
- Manager — доступ ко всем заявкам, выбор провайдера/агента, контроль исполнения
- Provider — только свои заявки; исполнение платежа (без ПДн клиента)

Статусы клиента (User):
- Новый клиент
- Активный клиент
- Заблокированный клиент
- Ожидающий обработки (красный/жёлтый рейтинг)

Документы (поля + автозаполнение):
1. Агентский договор — при добавлении компании клиента
2. Поручение принципала — при готовности к переводу
3. Отчёт агента — после исполнения перевода
4. Инвойс — основание суммы/валюты (загрузка клиентом)
5. Контракт — юр. основание сделки
6. Подтверждение оплаты — факт перевода

Флоу оформления заявки (шаги):
1. Начало сделки («Оставить заявку на платеж»)
2. Инвойс и контракт (PDF до 15 МБ) или ручной ввод номера/даты
3. Условия: импорт/экспорт, валюты, сумма, аванс/постоплата, товар/услуга, ТН ВЭД, дата отгрузки
4. Отправка → compliance
5. Подписание агентского договора и поручения (первая сделка)
6. Оплата клиентом агенту + опциональное подтверждение
7. Исполнение провайдером + отчёт агента
8. Закрывающие документы, подписание, COMPLETED

Статусы заявки (из документа):
- FORM_WAITING_VERIFICATION
- FORM_WAITING_CORRECTIONS
- FORM_ACCEPTED
- CANCELED_BY_COMPLIANCE_OFFICER
- COMPLETED
- (ожидание исполнения платежа и др.)

Специфика ВЭД:
- импорт/экспорт, ТН ВЭД, Incoterms
- аванс / постоплата
- фиат + крипто (RUB, USDT, BTC, ETH, CNY, USD, EUR…)
- курс, агентское вознаграждение, хеш/платёжка как подтверждение


================================================================================
2. ОЦЕНКА РЕПОЗИТОРИЕВ ОТНОСИТЕЛЬНО ДОКУМЕНТА
================================================================================

--------------------------------------------------------------------------------
2.1. fintech-platform — НАИБОЛЕЕ ПОЛЕЗЕН КАК БАЗА
--------------------------------------------------------------------------------
Что стыкуется:
- RBAC (auth-service: роли, права, назначение) — можно натянуть на 5 ролей из ТД
- статусы пользователя (active / blocked / pending) — близки к статусам клиента
- KYC/AML (kyc-service, документы, статусы) — паттерн для compliance, не готовый ВЭД-флоу
- payments / fx / ledger — каркас сумм, валют, переводов, курса
- connectors: Striga, Railsr, Bitso, Apaylo
- API gateway

Чего нет:
- заявки ВЭД, карточки компаний/контрагентов
- генерация агентских документов
- флоу менеджера/провайдера
- статусы FORM_*
- ТН ВЭД, инвойс/контракт как сущности сделки

Вывод: лучший кандидат на скелет платформы; доменную логику из ТД писать поверх.


--------------------------------------------------------------------------------
2.2. amg_all — ИНФРАСТРУКТУРА И ИНТЕГРАЦИИ
--------------------------------------------------------------------------------
Что полезно:
- микросервисы, Docker/compose, мониторинг
- интеграции провайдеров (Striga, RailsR, Bitso, Apaylo)
- JWT/auth, мультивалютность/крипто
- BDUI (динамические формы) — потенциал для формы заявки
- в Storybook — намёки на «проверку контрагента» (маркетинг/UI, не бизнес-логика)

Важно: в Doc.md указано, что готовность бизнес-логики ≈ 0% без детального ТЗ.
Готового ВЭД-цикла заявок/документов нет.

Вывод: брать паттерны деплоя, gateway, коннекторы; не ждать готовый продукт под ВЭД.


--------------------------------------------------------------------------------
2.3. AMG — ОГРАНИЧЕННО ПОЛЕЗЕН
--------------------------------------------------------------------------------
Ядро АБС: clients (в т.ч. ИНН), accounts, transactions + Docker/PostgreSQL + ML-дашборд.

Полезно как справочная модель «клиент–счёт–транзакция».
Не покрывает роли комплаенса/менеджера/провайдера, документы сделки и статусы заявки.


--------------------------------------------------------------------------------
2.4. AMG-Flow — СЛАБО РЕЛЕВАНТЕН ДОМЕНУ
--------------------------------------------------------------------------------
По сути AI/RAG-чат + аналитика (React + Go + Python + Ollama).
«Workflow» — заглушка; модели БД — сообщения чата.

Имеет смысл только если позже понадобится AI-ассистент для менеджера/комплаенса.


--------------------------------------------------------------------------------
2.5. 360Flow — ПОЧТИ НЕ РЕЛЕВАНТЕН
--------------------------------------------------------------------------------
Next.js UI (neo-360): welcome → dashboard → тарифы.
Нет backend, ролей, платежей/ВЭД.
Максимум — shadcn/UI-компоненты как визуальный стартер.


================================================================================
3. ПРИОРИТЕТ ПЕРЕИСПОЛЬЗОВАНИЯ
================================================================================

1. fintech-platform — auth/RBAC, KYC, payments, FX, ledger, API gateway
2. amg_all         — интеграции провайдеров, infra, BDUI
3. AMG             — схема клиент/счёт/транзакция (справочно)
4. AMG-Flow        — только если нужен AI-слой
5. 360Flow         — опционально UI-kit


================================================================================
4. ЧТО ПРИДЁТСЯ СТРОИТЬ С НУЛЯ (ГЛАВНЫЙ GAP)
================================================================================

1. Доменная модель заявки + state machine статусов
2. Ролевые кабинеты: internal/external compliance, manager, provider
3. Карточки компаний (принципал / контрагент) и привязка к заявкам
4. Генерация и подписание 6 типов документов
5. Wizard заявки (инвойс/контракт → условия → ТН ВЭД → отправка)
6. Назначение провайдера и подтверждение (хеш / платёжка)


================================================================================
5. ИТОГ
================================================================================

Документ описывает операционную ВЭД-платформу заявок и документов.
Из репозиториев ближе всего fintech-platform (каркас) + выборочно amg_all (интеграции/infra).
Готового совпадения с процессной моделью из ТД нет — её нужно проектировать отдельно.

Возможные следующие шаги:
- карта «требование из ТД → что берём из какого репо → что пишем с нуля»
- MVP-срез по ролям/статусам
