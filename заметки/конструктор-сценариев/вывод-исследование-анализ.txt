Конструктор сценариев — исследование и анализ
Дата: 2026-09-17
Контур: продукт кабинетов (vdp)
Виды работы: исследование + анализ (без разработки)
Статус: принято человеком 2026-09-17

Зачем
Менеджер хочет самостоятельно собирать автоматизацию, когда нужна другая логика цепочки заявки. Сейчас почти каждый новый сценарий идёт через разработку — дорого и долго.

Уже решено (не переоткрывать)
Этап 1. Сборка на базе текущих знаний и рычагов платформы.
Этап 2. Кастом через инструменты/vedy_bot — только после того, как этапа 1 не хватает.
Не ломаем созданное. Этапы последовательны.

────────────────────────────────────────
1. ИССЛЕДОВАНИЕ — карта рычагов без кода

Что уже меняет «логику цепочки» без нового кода

A. Участие ролей (RoleProcessConfig / process-roles)
Кто меняет: суперадмин (root), API PUT /api/v1/admin/process-roles/… — не менеджер сделки.
Что можно: включить / выключить необязательную роль; приоритет среди ролей; capabilities / influence.
Что нельзя: переставить этапы статуса; выключить обязательную роль-актор этапа; вставить новый шаг «между» статусами.
Пилот по умолчанию: ICO и ECO выключены; менеджер закрывает их шаги (continuity) на тех же статусах.
Опциональные слоты в каталоге: sales, viewer; treasurer — по process config на денежных маршрутах; bank — канал создания заявки.

B. Выбор маршрута сделки (конфиг заявки, не BPM)
Импорт advance — клиент платит до провайдера; казначей подтверждает покрытие.
Импорт post_payment / POSTPAY_RATE_ON_PP — провайдер раньше рублёвого покрытия; курс и комиссия после ПП.
Экспорт PAY_FROM_EXPORT — отдельная казначейская лестница до completed.
Ветки по действиям менеджера (уже в машине статусов): corrections, refund, shipment (опционально), provider return.
Источник: vdp/docs/domain/form-lifecycle.md

C. Именованные сценарии (каталог / согласование)
Справочник vdp/docs/pilot/scenario-role-directory.md и тексты в заметки/согласование сценариев/.
Это контракт приёмки и автотестов + язык для менеджмента, а не UI-конструктор.
Spine пилота: клиент + менеджер + провайдер до completed + возврат на доработку.
Менеджер «собирает» путь операционно: continuity / reject / payment / assign provider / report / опционально shipment — внутри уже заложенных переходов.

D. Кто сейчас «конструктор»
Root — конфиг ролей процесса.
Менеджер — операционные решения по заявке и выбор ветки там, где CTA уже есть.
Клиент при создании — direction / payment_method (где UI/API это дают).
Разработка — любой новый статус, новый участник-актор с новыми переходами, новая денежная методология вне готовых лестниц.

────────────────────────────────────────
2. ИССЛЕДОВАНИЕ — граница «конструктор» vs фиксированный процесс

Источник истины статусов — домен form-payment. UI — проекция.
Process policy уже зафиксировал: BPM-редактор этапов и выключение обязательных gates из админки запрещены.
«Другая логика цепочки» в безопасном смысле = другая сборка из разрешённых рычагов (роли + маршрут оплаты + ветки), а не произвольный граф статусов.

Рабочее определение этапа 1
Конструктор сценариев (этап 1) — сборка рабочего маршрута заявки из уже существующих рычагов: process-roles, continuity, денежные лестницы, ветки corrections / refund / shipment / provider return, именованные сценарии каталога. Не свободный BPM.

────────────────────────────────────────
3. ИССЛЕДОВАНИЕ — роль vedy_bot как этап 2

Зачем этап 2
Когда рычагов этапа 1 не хватает: новый участник с новыми полномочиями на статусах; новая ветка / денежная методология; автоматизация вне текущего lifecycle.

Как стыкуется
vedy_bot — канал запроса и подготовки кастома (intake → знания → план / агент / HITL), а не второй источник истины статуса кабинетов.
Бот не должен «на лету» подменять статусную машину VDP. Кастом = отдельная поставка (план → разработка / конфиг → релиз), согласованная с «не ломаем созданное».
Менеджеру на этапе 2 — запрос «нужна другая логика»; оператору / разработке — превращение в изменение продукта без обхода AuthZ и денег.

────────────────────────────────────────
4. АНАЛИЗ — зазор желание ↔ платформа

Желание менеджера → статус сегодня

Убрать ECO / ICO из повседневного пути
Уже: process-roles (root) + continuity менеджера. Пилот так и работает.

Включить казначея / sales / viewer в участие
Частично: process-roles (root). Sales по умолчанию выключен (observer). Менеджер сам слоты не переключает.

Другой порядок оплаты (аванс / постоплата / экспорт)
Уже в рамках готовых лестниц (выбор метода / направления сделки). Новые режимы (например POSTPAY_FIXED_RATE) — только код.

Вернуть на доработку / возврат денег / отгрузка
Уже: ветки в домене + CTA менеджера. Это не «новый сценарий в коде», а выбор ветки.

Свой сценарий с новым участником-актором (меняет статусы)
Только код / этап 2. Нельзя «вставить роль вместо ECO» конфигом так, чтобы сменилась методология.

Произвольный порядок этапов («сначала платёж, потом комплаенс»)
Нельзя конфигом. Только изменение домена (релиз). Противоречит зафиксированной process policy.

Автоматизация «собрал в UI и сразу едет в проде»
Нет такого продукта. Каталог сценариев — для проверки и согласования, не конструктор runtime.

Риски «не ломаем созданное»
Обещать «полный конструктор» = ложное ожидание и давление сломать фиксированный процесс.
Свободный граф статусов бьёт AuthZ, идемпотентность денег, инварианты refund / FundsHeld.
Новый участник с ПДн у Provider — нарушение границы ролей.
Правки process-roles mid-flight не должны мигрировать статусы уже идущих заявок (уже заложено: version stamp).
Путать каталог scenarioverify (тесты) с продуктовым конструктором для менеджера.

────────────────────────────────────────
5. АНАЛИЗ — рекомендация и следующий шаг

Продуктовая формулировка этапа 1 (что говорить менеджеру)
«Вы собираете рабочий путь заявки из готовых рычагов: кто участвует (через настройки ролей процесса у суперадмина), какой денежный маршрут у сделки, какие ветки открыть по ходу (возврат на правки, возврат денег, отгрузка). Новые виды участников и новые этапы процесса — отдельный кастом, не кнопка в кабинете.»

Что явно не обещаем до отдельной разработки
Свободный редактор порядка статусов.
Выключение обязательных gates «из админки» вопреки StageBinding.
Самостоятельное создание менеджером новой роли-актора с переходами статусов.
Runtime-автоматизация из vedy_bot без релиза в VDP.

Критерий перехода к этапу 2 (vedy_bot / кастом)
Запрос не закрывается комбинацией: process-roles + существующий маршрут оплаты + существующие ветки + continuity.
Или нужен новый участник / новая ветка / новая автоматизация вне lifecycle.
Тогда: запрос через vedy_bot (или тот же канал intake) → разбор → план разработки; статусная машина кабинетов не меняется ботом напрямую.

Что утвердить до любой будущей волны «Разработка»
1. Согласие с определением этапа 1 (сборка из рычагов, не BPM).
2. Кто операционно владеет process-roles: остаётся root (рекомендация) или отдельный безопасный subset для менеджера (это уже отдельный product decision + код).
3. Чеклист «сначала этап 1»: типовой запрос менеджера прогоняется по таблице зазора выше; в этап 2 только если не закрыт.
4. Язык для менеджмента: не «конструктор всего», а «сборка маршрута из готовых сценариев / ролей / лестниц».

Один следующий шаг
Утвердить это определение этапа 1 и критерий перехода к этапу 2 (приёмка человеком). После «ок» — при необходимости отдельный plan только на разработку (например UI подсказки «какой рычаг выбрать» или расширение прав менеджера на subset process-roles); в этой волне кода нет.

────────────────────────────────────────
Краткий вывод исследования

Узнали: платформа уже даёт заметную «другую логику» без кода — через роли процесса, continuity, денежные лестницы и ветки. Жёсткая граница — фиксированная машина статусов и запрет BPM из админки. Каталог сценариев — согласование и тесты, не конструктор runtime. vedy_bot уместен как этап 2 для кастома вне рычагов, без подмены домена.

Рекомендуем: позиционировать «конструктор» как этап 1 — сборка из разрешённых рычагов; не обещать свободный BPM; этап 2 — только когда чеклист этапа 1 не закрывает запрос.
