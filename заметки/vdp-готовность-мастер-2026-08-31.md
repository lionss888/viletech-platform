# Часть A — FE↔API (приоритет №1)

## A.1. Интеграцию сделали?

**Нет — в коде `vdp/fe` интеграции с core нет.**

| Что есть (инфраструктура) | Что есть в коде (демо) |
|---------------------------|-------------------------|
| `vite.config.ts` — proxy `/api` → `localhost:8080` | `store.tsx` — `localStorage` `ved-demo-state-v2` |
| Доки: `app-vs-demo.md`, `api/overview.md` | `mock.ts` — seed |
| Backend готов для `compose-e2e` | Все routes → `useVed()`, не HTTP |
| | `login.tsx` — локальный `ROLES`, не `POST /auth/login` |
| | `applyAction()` — только localStorage |
| | `forms.new.tsx` — mock, не `POST /forms` |

Папки `/demo/*` **нет** — весь UI = демо. Grep `fe/src`: нет `api/v1`, `vdp-auth`, API-клиента.

## A.2. Почему казалось, что интеграция есть

1. Доки описывают **platform-store bridge** и JWT — план, не код в `fe/src`.
2. Proxy настроен — компоненты API не вызывают.
3. Backend: auth, forms, actions, files, nest-parity — всё в Go e2e.

## A.3. Расхождение action id

| Слой | Id | Пример |
|------|-----|--------|
| FE `actions.ts` | UI | `accept_form`, `ico_form_start`, `mgr_assign_provider` |
| Core | домен | `submit`, `ico_start` + отдельные endpoint'ы |

Маппинг **не реализован** (нет `platform-store`, нет `action-bridge.test` в fe).

Manager-действия часто **не** `POST .../actions/{action}`:

- `POST /api/v1/forms/{id}/agent`, `/provider`, `/rate`, `/commission`
- `POST .../contract/manual-attach`
- Nest-parity `PUT /api/v1/{role}/form-payment/{id}/...`
- `POST /api/v1/file-store/upload` + attach

## A.4. Расхождение моделей данных

**API:** `organization_id`, `invoice_amount`, `docs_json`, `channel` — нет `number`, `timeline[]`, `documents[]`, `amountMinor`, `condition`.

**FE mock:** `number`, `amountMinor`, `condition`, `documents`, `timeline`, display names.

Нужен **mapper** или смена UI на raw API. Backend **не отдаёт** `allowed_actions` в GET form.

# Часть B — Пункт 1: вводные

**Что это значит:** вводные — контракт «что заказчик ожидает в продукте». Backend (`vdp/core`, `vdp/hub`) проектировался под ТЗ. Frontend (`vdp/fe`) — **демо на mock**, не подключён к API.

**Оценка:** backend ~**82–85%**, продукт (UI+API) ~**55–60%**.

### Общая картина (что значит «вводные выполнены»)

**Для заказчика:** пользователь каждой роли проходит сценарии в **рабочем кабинете**, документы и статусы совпадают с ТЗ, деньги и роли защищены на сервере.

**Факт сейчас:**

- **Backend (~82–85%):** машина статусов, роли, 331/331 parity, refund, bank, contracts R3, multi-order, file ACL, provider projection без ПДн.
- **Продукт (~55–60%):** UI (`vdp/fe`) — демо на `localStorage` + `mock.ts`, **не вызывает** `/api/v1/*`.
- **Разрыв:** заказчик не может принять «платформу ВЭД» по кабинетам, пока не закрыт FE↔API (часть A).

**Главный вывод:** большинство пробелов в глазах бизнеса — не «дописать ещё 50 endpoint'ов», а **подключить UI к уже существующему API** и довести документы/интеграции на staging.

## B.1. Роли и статусно-ролевая модель

### Что требуют вводные

- 5 ролей: User, Internal CO (ICO), External CO (ECO), Manager, Provider.
- У каждой — зона видимости и набор действий.
- У User — статусы организации: новый / активный / заблокированный / ожидающий обработки (красный/жёлтый рейтинг).
- У заявки — машина статусов от черновика до `completed`: договоры, поручения, платежи, возвраты, отгрузка.

### Что сделано (backend)

- Роли и AuthZ в use case / HTTP, не только UI.
- Машина статусов в домене `formpayment`, unit + gate-тесты.
- ICO / ECO разделены.
- Provider: `ProjectForProvider`, `ForbiddenPIIKeys`.
- Рейтинг и очередь: `GET /api/v1/organization?rating=&awaiting_processing=`.

### Что сделано частично

- Статусы org в UI — mock + `localStorage`, не backend.
- «Следующий шаг» — `actions.ts` локально, не матрица API.

### Что не сделано / слабо

- Нет продукта «роль → кабинет → реальные данные»; браузер ≠ `compose-e2e.sh`.
- ICO journey нет в Playwright.
- Block/unblock/unblock-request — API есть, UI e2e не проверен.

### На что влияет

- **UAT:** backend через Postman/e2e; **кабинет** — только после FE↔API.
- **Приёмка:** заказчик подписывает экраны, не «331 маршрут Go». **Разрыв №1.**

### Что нужно сделать

1. Программа FE↔Core: JWT, API client, замена mock/store.
2. Playwright smoke per role на real API.
3. Сверка UI-кнопок с API (403 чужой роли).

## B.2. Документы (агентский, поручение, отчёт, инвойс, контракт)

### Что требуют вводные

- Автогенерация PDF по шаблонам из карточек.
- Разные шаблоны по ПА.
- Скачать → подписать → загрузить; менеджер проверяет.
- XLSX Nest-совместимость.

### Что сделано

- `docs_payload.go` + `template_id` / `template_file_id` per PA.
- Hub + `DOCS_URL`; без URL — `stub.pdf`.
- XLSX — real OOXML (`MinimalXLSX`).
- Files API + ACL.

### Что сделано частично

- PDF quality = docs-сервис; dev = stub.
- Полнота полей (ФИО, Incoterms, строки товаров) — шаблоны не сверены на staging.

### Что не сделано

- Docs-сервис не в репо «из коробки» — только `staging-env.example`.
- UI upload/download не через API.

### На что влияет

- Пилот: stub PDF ок с оговоркой.
- Prod/юридическая приёмка: нужны DOCS_URL + шаблоны ПА.
- Менеджер не проходит полный цикл поручения в UI на реальных данных.

### Что нужно сделать

1. Staging DOCS + `staging-smoke.sh`.
2. Шаблоны per PA (версия/дата — расширение §1.3).
3. FE: files + docs events.
4. UAT: сверка полей ТЗ с PDF.

## B.3. Договоры: типы, шаблоны ПА, ручная загрузка (расширение §1–2)

### Что требуют расширенные вводные

- Типы: агентский / субагентский / услуги.
- Шаблон по ПА; ветки `CONTRACT_*`.
- Manual attach с auto-confirm.
- `on_behalf_organization_id`; история; деактивация.

### Что сделано (backend)

- `Contract`: agency/subagency/services, `history_json`, deactivated.
- `POST .../contract/manual-attach`, `manual_attach_auto_confirm`.
- Валидация subagency без on_behalf → ошибка.
- Gate R3 ParityDone.

### Что сделано частично

- `history_json` в БД, нет UI аудита.
- Admin смена типа — API возможно, FE упрощён.

### Что не сделано в продукте

- UI выбора типа при manual attach.
- Шаблон клиенту после выбора ПА.
- Деактивация → `CONTRACT_WAITING_CORRECTION` в UI/E2E.

### На что влияет

- Backend готов для интеграционного теста; кабинет — нет.
- Риск расхождения demo payload vs prod API.

### Что нужно сделать

1. FE: manual-attach form (тип, file, on_behalf).
2. FE: org card — тип, история.
3. E2E: субагентский → поручение без ожидания клиента.

## C.1. `чистая-архитектура`, `use-cases`, `solid`, `screaming-architecture`

### Требование

- Статусы и матрица ролей — в домене; UI только проекция.

### Соблюдается (backend)

- `formpayment` machine; services по действиям (`contract.go`, `form_payment_assign.go`, refund).

### Нарушается (frontend)

- UI хранит истину в `localStorage` — нарушение `чистая-архитектура`, `интеграция-и-события`.
- `applyAction` минует домен.

### Что делать

- Все переходы через `POST .../actions` (+ спец. endpoints); optimistic UI с rollback.
- Не дублировать матрицу в `actions.ts` — `allowed_actions` из API или refetch.
