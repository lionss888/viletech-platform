## Критерий преемственности (DoD)

1. Клиент создаёт заявку и отправляет менеджеру на ревью.
2. Менеджер возвращает на доработку **или** отправляет провайдеру.
3. Провайдер завершает **или** возвращает менеджеру (уточнения / отклонение).
4. Root включает доп. участника в слот фиксированного процесса; 1–3 остаются выполнимы с учётом новых gate.

**Граница:** не BPM новых статусов — только enable/mandatory/priority/influence/caps на существующих слотах.  
**Честно:** стержень пилота U→M→P, не полный Nest lifecycle.

## 0. Подготовка

- [ ] Войти root → `/process-roles`: нет роли root в списке участников
- [ ] ICO и ECO: «в процессе» = нет
- [ ] User, Manager, Provider: «в процессе» = да
- [ ] Выйти

---

## 1. Клиент → менеджер

- [ ] Войти **user**
- [ ] `/forms/new` — создать заявку (товар, документы или «нет документов» по правилам формы)
- [ ] Отправить / submit
- [ ] Заявка ушла с черновика; виден статус «ожидает / у менеджера» (не зависла на compliance)
- [ ] В карточке **нет** выбора/списка провайдеров
- [ ] Запомнить **номер / id** заявки → выйти

**Pass:** клиент создал и отправил; путь не упёрся в ICO/ECO.

---

## 2a. Менеджер → возврат клиенту

- [ ] Войти **manager**, открыть ту же заявку
- [ ] Есть действие вроде «вернуть / на доработку / отклонить форму»
- [ ] Выполнить возврат
- [ ] Статус у клиента на доработке
- [ ] Выйти → **user** → заявка снова доступна для правок / повторной отправки

**Pass:** ветка «менеджер вернул».

---

## 2b. Менеджер → провайдер

*(новая заявка или та же после повторного submit)*

- [ ] **user** → снова submit до очереди менеджера
- [ ] **manager** → принять/продвинуть форму (без шага ICO)
- [ ] Назначить провайдера / отправить провайдеру
- [ ] Заявка у провайдера / «ожидает исполнения»
- [ ] Выйти

**Pass:** ветка «менеджер отправил провайдеру» без soft-lock.

---

## 3a. Провайдер → возврат менеджеру

- [ ] Войти **provider**, открыть заявку
- [ ] Нет ПДн клиента (ФИО/паспорт/личные контакты досье)
- [ ] Принять в работу (если есть)
- [ ] Вернуть менеджеру (уточнение / return)
- [ ] Статус снова у менеджера
- [ ] **manager** видит заявку и может действовать дальше

**Pass:** ветка «провайдер вернул».

---

## 3b. Провайдер → завершение

*(отдельная заявка до этапа провайдера)*

- [ ] Довести U→M→assign P
- [ ] **provider** → исполнить / подтвердить по доступным кнопкам до закрытия этапа провайдера
- [ ] Заявка не зависла; менеджер/клиент видят ожидаемый следующий статус

**Pass:** ветка «провайдер завершил» (в объёме пилотного стержня).

---

## 4. Root включает доп. участника; 1–3 всё ещё живы

- [ ] **root** → `/process-roles`
- [ ] Включить ICO (или ECO): «в процессе» = да; при необходимости «обязательная» = да
- [ ] Сохранить / убедиться, что флаги держатся после обновления страницы
- [ ] **user** → новая заявка → submit
- [ ] **manager** **не** может обойти шаг включённого ICO (кнопки advance/approve ICO недоступны или API/UI отказывают)
- [ ] **ico@vdp.local** / `ico` → пройти шаг review/approve
- [ ] Далее **manager** → провайдер (как в п.2b) — путь снова идёт
- [ ] Опционально: выключить «в процессе» у ICO → `mandatory` сбрасывается; стержень U→M→P снова без gate ICO

**Pass:** включение участника добавляет gate на существующем слоте; после прохождения 1–3 снова выполнимы. Не появляется новый BPM-статус «с нуля».

---

## 5. Быстрые негативы (рядом с DoD)

- [ ] Чужая роль: **user** не назначает провайдера; **provider** не видит чужие неassigned заявки
- [ ] Клиент по-прежнему не видит провайдеров в UI заявки
- [ ] Compliance при выключенных ICO/ECO не блокирует пилотный стержень
