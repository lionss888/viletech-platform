## Аксиома

Мерим не количество кода. Мерим **скорость реализации запросов заказчика**: от формулировки запроса до проверяемого результата у роли на среде (localhost → зелёный Local QG → alpha / приёмка).

Строки кода, число коммитов и размер diff — только диагностика, не KPI.

## Единица работы

| Поле | Смысл |
|--|--|
| Запрос | Одно предложение языком роли: кто что сможет сделать после среза |
| Acceptance | Как человек проверит на экране (роль → жест → ожидаемый результат) |
| Срез дня | Кусок запроса, который укладывается в ≤ 24 ч вместе с gate |
| Gate | Имя Local QG / make: `ci-pr` / `ci-pr-pilot` / `ci-main` |
| Lead time | Часы от «взяли в работу» до «Acceptance на alpha» (или localhost, если выкат ещё не в scope среза) |
| Rework | Повторный заход после заявления «готово» по тому же запросу/срезу |

Запрос заказчика закрыт только когда Acceptance пройден. Зелёные unit без Acceptance — не закрытие.

## Целевой ритм поставки

**Один проверяемый срез на alpha не реже одного раза в 24 часа** (календарные сутки работы), если нет явного блокера среды/секретов.

Не значит «один огромный PR в сутки». Значит: каждый рабочий день есть выкат с ценностью для роли, даже маленький.

Бюджет суток (порядок):

- Реализация среза: 4–6 ч
- Local QG по DoD: 1–4 ч (зависит от `ci-pr` / `ci-pr-pilot` / `ci-main`)
- Путь CI → Images → Deploy и проверка alpha: 1–2 ч
- Итого срез должен быть нарезан так, чтобы сумма укладывалась в день

Срезы с обязательным `ci-main` или `release-gate` планировать отдельно: не каждый день.

## Как оценивать новую задачу (чеклист)

1. Сформулирован **Запрос** языком роли?
2. Есть **Acceptance** (не «тесты зелёные»)?
3. Срез ≤ суток с **именем gate** в DoD?
4. В том же diff — тесты слоёв, которые срез ломает?
5. Не смешаны в одном push три поверхности (домен + новый e2e вне smoke + yaml CI) без крайней нужды?
6. После «готово» — зелёная кнопка Local QG из DoD, затем Acceptance?

Если пункт 3 «нет» — задача не готова к оценке в сутках: сначала нарезать.
