================================================================================
ВЕРДИКТ
================================================================================

ДА — брать fea-stage-vf2 как уверенный backend-ядро ВЭД.
Это сильнее sandbox fea@prod / v360/fea-stage: тот же Fea360-домен + Internal CO
+ модули counterparty / hs-code / diadoc / treasurer-task / payment-order-generation
и отчёт API (~356 endpoints) — удобная опора под BD generated UI с нуля.

Фронт Nuxt из sandbox НЕ нужен при BDUI с нуля.

================================================================================
ПОКРЫТИЕ ВВОДНЫХ ОТ ВИ
================================================================================

Роли ВИ → в коде:
  User                         → USER
  Internal compliance officer  → INTERNAL_COMPLIANCE_OFFICER (+ web controllers)
  External compliance officer  → COMPLIANCE_OFFICER
  Manager                      → MANAGER
  Provider                     → PROVIDER (+ зона provider: req.account._id)

Статусы ВИ (FORM_WAITING_VERIFICATION / CORRECTIONS / FORM_ACCEPTED /
CANCELED_BY_COMPLIANCE_OFFICER / COMPLETED) — есть; плюс StageHash
(import/export × аванс/постоплата).

Документы ВИ:
  агентский договор / поручение / отчёт агента — генерация + шаблоны
  инвойс / контракт / подтверждение оплаты — файлы + поля заявки
  Диадок (VF-2) — уже в этом снимке (сверх ВИ, но готово)

Условия сделки ВИ: IMPORT/EXPORT, ADVANCE/POST_PAYMENT, товар/услуга, hsCode —
есть (модуль hs-code сильнее, чем в старом prod).

================================================================================
ЧТО УЧЕСТЬ ПРИ BDUI С НУЛЯ
================================================================================

1. API — REST-кабинеты по ролям (site / internal-co / co / manager / provider…),
   не готовые screen-schema для BDUI. BDUI-слой строить поверх доменных
   статусов/действий и api-endpoints-report.md, не копировать Nuxt.

2. Provider DTO всё ещё отдаёт полный account — против ВИ («без ПДн клиента»).
   Перед банковским UI — узкий DTO (реквизиты, инвойс, суммы, хеш/платёжка).

3. Роли сверх ВИ (TREASURER, ONE_C, SENIOR_PROVIDER, ROOT…) — не рисовать в MVP BDUI.

4. Тесты гуще, чем у v360, но в основном вокруг Diadoc; табличные тесты
   StageHash + права ролей всё ещё желательны (правила-построения).

5. Incoterms в ВИ заявлены явно; в коде опора слабее, чем у hsCode — проверить
   поля при проектировании шага «условия сделки».

================================================================================
АЛЬТЕРНАТИВЫ В ТОМ ЖЕ РЕПО
================================================================================

sandbox fea@stage — НЕ брать: там снят Internal CO (против ВИ)

Рекомендация: зафиксировать backend = fea-stage-vf2 @ bea428b1;
