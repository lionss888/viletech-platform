## 2. Качество реализации и стабильность

### Сильные стороны

1. **Тестовая пирамида** — SM/authz/outbox unit; HTTP gates R1–R12; один compose/integration path.
2. **Честные gate'ы** — `endpoint_matrix_test`, `r12_verification_test`, rule [`честность-готовности`](../.cursor/rules/честность-готовности.mdc).
3. **Границы контекстов** — Provider DTO без ПДн проверяется (`ProjectForProvider`, `ContainsPII`).
4. **Локальная воспроизводимость** — `docker compose`, Postgres by default, `make integration-gate`.

### Риски

1. **Stub маскирует глубину** — 200 OK без реального docs/mail/xlsx на prod-контуре.
2. **Postgres coverage** — многие тесты на memory; integration postgres — точечный.
3. **Нет CI** — регрессии зависят от ручного `make integration-gate`.
4. **Dev-секреты в compose** — `JWT_SECRET`, `HUB_SHARED_SECRET` для dev only.
5. **Observability** — structured log есть; tracing/алерты/семантический мониторинг «зависших заявок» не оформлены.
6. **Lovable + dual contour** — app/demo; история ветки связана с Lovable (см. `vdp/fe/AGENTS.md`).

## 3. Готовность к передаче заказчику

### A. Пилот / demo / UAT — ~65–70%

**Можно передавать**, если заказчик принимает ограничения:

- Seed-аккаунты (`user@vdp.local` / `user`, `manager`, `ico`, `eco`, `provider`, `bank`, `root`).
- OCR/документы/почта/TG — stub или dev-hub без prod URL.
- XLSX — placeholder.
- Copy на финальных шагах может расходиться между кабинетами до закрытия **RW9**.
- Запуск: `cd vdp && make compose-up`; инструкции — `vdp/fe/README.md`.

**Пакет для передачи на пилот уже есть:** compose, README, seed, role-debug, unit + compose-e2e gates (Makefile).

| Блок | Статус |

| Реальные интеграции (Diadoc, OCR, банк, mail) | Stub / конфигурируемые адаптеры |
| Copy consistency (RW9) | Не закрыт |
