--------------------------------------------------------------------------------
2.1. frontend (Nuxt 3) — ВЫСОКАЯ ЦЕННОСТЬ
--------------------------------------------------------------------------------

Кабинеты:
- client: создание сделки, стадии S0–S5, загрузка/подписание документов
- admin: проверка сделок, пользователи, реквизиты, роли админов

Роли (RoleType):
- CLIENT
- SUPER_ADMIN
- COMPLIANCE_OFFICER
- OPERATION_MANAGER
- VALIDATION_MANAGER

Стадии сделки (DealStage):
LIMITS → REVIEW → INVOICE → PAYMENT → EXECUTION → ACT → COMPLETED / CANCELLED

Статусы бэкенда (DealStatus), фрагмент:
PENDING_REVIEW_CO, REVIEW_CO, PENDING_REVIEW_OM, REVIEW_OM,
INVOICE_*, PENDING_FUNDS, WAITING_EXECUTION, DEAL_EXECUTION,
ACT_*, DEAL_COMPLETED, DEAL_CANCELLED

Документы в UI:
- invoice (prefilled / signed)
- payment order (поручение) — funds / execution
- act (акт / закрывающий)
- подтверждение: DOCUMENT или HASH (txid)

Маппинг на ТД (приблизительно):
ТД User                    ≈ CLIENT
ТД Internal/External CO    ≈ COMPLIANCE_OFFICER (+ VALIDATION_MANAGER как доп. слой)
ТД Manager                 ≈ OPERATION_MANAGER
ТД Provider                ≈ роль PSP / исполнение (см. monorepo PSP_MANAGER)
ТД FORM_WAITING_*          ≈ PENDING_REVIEW_* / NEED_CLARIFICATION
ТД поручение / отчёт       ≈ payment_order / act (другая терминология продукта)
ТД инвойс                  ≈ invoice (есть)

Что полезно переиспользовать:
- UX флоу сделки и progress по стадиям
- ролевые кабинеты client/admin
- формы реквизитов (CIS / INTERNATIONAL / crypto)
- загрузка и подписание файлов
- API-контракты exchange/auth/legal


--------------------------------------------------------------------------------
2.2. monorepo (Go, Crypto 360) — ВЫСОКАЯ ЦЕННОСТЬ (backend)
--------------------------------------------------------------------------------

Сервисы:
- auth-users  — пользователи, KYB/SumSub, админы, PSP providers
- exchange    — сделки, курсы, invoice/act/execution/funds, state machine
- legal       — шаблоны документов, генерация PDF (Gotenberg), SoF, registration docs
- notification

Роли в shared/jwt (важное отличие от frontend enum):
+ PSP_MANAGER — ближе всего к Provider из ТД

Сущность PSPProvider: company_name, inn, signatory, license

Документы:
- стратегии генерации Invoice / Act / Archive / TransactionHash
- document_template + document в legal
- PDF через external/gotenberg

Интеграции: SumSub, S3, Bequant, FastForex, Gotenberg

Что полезно:
- готовый state machine сделки + review CO/OM
- генерация документов по шаблонам
- RBAC с compliance / operation / validation / PSP
- KYB/онбординг компаний
- паттерн monorepo Go + docker-compose

================================================================================
3. СОВПАДЕНИЯ И РАЗРЫВЫ С ТД
================================================================================

СИЛЬНОЕ СОВПАДЕНИЕ (брать как основу процесса):
[+] статусно-ролевая модель сделки
[+] compliance → manager → исполнение
[+] клиентский wizard + админские решения
[+] документы + подписание + подтверждение платежа (файл/хеш)
[+] фиат + крипто, реквизиты, курс/комиссия
[+] генерация PDF по шаблонам

ЧАСТИЧНОЕ СОВПАДЕНИЕ (адаптировать):
[~] роли названы иначе (нет явного Internal/External CO и Provider;
    есть CO / OM / Validation / PSP_MANAGER)
[~] документы: invoice + act, а не агентский договор / поручение принципала /
    отчёт агента из ТД — нужна смена шаблонов и полей под ВЭД
[~] статусы FORM_* из ТД ≠ DealStatus из Crypto 360 — нужна карта переименований

НЕТ В SANDBOX (строить под ВЭД):
[-] импорт/экспорт как тип сделки
[-] ТН ВЭД, Incoterms
[-] аванс / постоплата
[-] карточка контрагента (иностранная организация) как отдельная сущность ТД
[-] раздельные флоу internal vs external compliance officer
[-] агентский договор при добавлении компании клиента (как в ТД)


================================================================================
4. ПРИОРИТЕТ ОТНОСИТЕЛЬНО ПРЕДЫДУЩИХ РЕПО (GitHub)
================================================================================

1. sandbox6902635/frontend + monorepo   ← главный кандидат (домен сделок)
2. fintech-platform                     ← auth/payments/FX/ledger каркас
3. amg_all                              ← интеграции провайдеров / infra
4. gitlab AMG / GitHub AMG              ← справочно АБС-схема
5. AMG-Flow / 360Flow / design-system   ← почти не релевантны

Практическая рекомендация:
использовать sandbox (Crypto 360) как процессный прототип/базу для ВЭД-платформы,
перенастроить домен (документы, поля, роли, статусы) под ТД банка,
а не собирать флоу сделок с нуля из fintech/AMG.


================================================================================
5. ИТОГ
================================================================================

gitlab AMG — мало полезен для ТД (АБС-ядро).

sandbox6902635 — ключевой источник:
frontend = готовый UI кабинетов сделок;
monorepo = backend state machine + документы + роли.

Это ближе всего к описанной в ТД операционной платформе заявок.
Основная работа — доменная адаптация под ВЭД (агентские документы,
ТН ВЭД, internal/external compliance, контрагент), а не изобретение
процессного каркаса.
