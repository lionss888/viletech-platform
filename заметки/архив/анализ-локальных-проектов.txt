Локальные проекты vs ТД ВЭД + ответ про ссылки sandbox
Дата: 24.08.2026

Ссылки на репозитории внутри sandbox — ДА, помогут.
Группа закрытая; без списка проектов можно пропустить репозитории.
Уже найдены: frontend, monorepo, пустой design-system.


================================================================================
1. Documents/_Exchange Platform
   remote: github.com/lionss888/_Exchange-Platform
================================================================================

Что это:
Криптообменник (fiat↔crypto) с KYC/AML.
Frontend: Nuxt 3. Backend: NestJS. PostgreSQL + Redis + MongoDB.

Роли:
- User
- ExchangeManager
- ComplianceOfficer
- Root

Статусы сделки — ПРЯМОЕ совпадение с формулировками ТД:
- form_waiting_verification   (FORM_WAITING_VERIFICATION)
- form_waiting_corrections    (FORM_WAITING_CORRECTIONS)
- form_accepted               (FORM_ACCEPTED)
- wallet_*                    (проверка кошелька комплаенсом)
- client_payment_*            (подтверждение оплаты клиентом)
- platform_payment_*          (исполнение платформой)
- completed / canceled_by_user / canceled_by_manager

UI: отдельные кабинеты клиента и админа; таблицы сделок для manager vs compliance;
инвойс, платёжное поручение, hash транзакции, AML-проверка кошелька.

Полезность относительно ТД: ОЧЕНЬ ВЫСОКАЯ как процессный шаблон заявки.
Это ближайший Nest/Nuxt-клон языка статусов из документа.

Разрывы с ТД:
- нет Internal/External compliance, нет Provider
- нет агентского договора / поручения принципала / отчёта агента как в ТД
- нет импорт/экспорт, ТН ВЭД, Incoterms, аванс/постоплата
- нет карточки иностранного контрагента
- продукт = обмен, не агентские ВЭД-платежи

Практический вывод:
ТД банка говорит языком Exchange Platform (FORM_WAITING_*),
а sandbox (Crypto 360) даёт более зрелую ролевую/документную машину.
Имеет смысл трактовать их как два поколения одного процессного продукта
и адаптировать под ВЭД-документы из ТД, а не писать state machine с нуля.
