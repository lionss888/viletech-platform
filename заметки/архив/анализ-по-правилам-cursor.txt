Повторный анализ источников vs ТД ВЭД с учётом .cursor/rules
Дата: 24.08.2026

Правила, которыми пересмотрен вывод (не «ещё один чеклист фич»):
- границы-и-контексты
- интеграция-и-события
- безопасность-ролей-и-данных
- устойчивость-и-наблюдаемость
- машинное-обучение
- правила-построения + nestjs-testing / nestjs-modules
- лучшие-практики
- UX (когнитивная нагрузка, формы/навигация, скорость)

Стек-специфика Go/Playwright учитывается точечно. Выбор базы не меняется от UX-законов; UX задаёт, как не ломать кабинеты при доработке.

Предыдущие заметки (fintech как «главная база», frontend sandbox как «только Crypto 360», exchange как «очень полезен для ТД») — частично устарели. Актуальная пара веток: заметки/анализ-всех-веток-sandbox.txt.


================================================================================
1. ВЫВОД ПОСЛЕ ПРАВИЛ (коротко)
================================================================================

База реализации для отдела ВЭД — модульный монолит Fea360:
  backend:  sandbox6902635/fea @ prod  (= аудит / v360/fea-stage / fea-stage.zip)
  frontend: sandbox6902635/frontend @ stage|develop  (ВЭД-кабинеты)
            + пара к аудиту: frontend @ release_10 или v360/frontend-stage

Не начинать с нарезки микросервисов из fintech-platform / amg_all.
Не брать fea @ stage/dev как единственный backend: там снята роль Internal compliance — прямо против ТД и правила ролей.

Чего в коде fea нет относительно правил (делать при реализации, не «потом когда разрежем сервисы»):
1) тесты переходов статусов и прав ролей (сейчас почти нет unit по домену);
2) отдельный DTO провайдера без ПДн клиента;
3) вынести recognition (OCR/Anthropic) с транзакционного пути заявки;
4) идемпотентность действий оплаты провайдера;
5) корреляция логов/очередей по id заявки.


================================================================================
2. ГРАНИЦЫ И КОНТЕКСТЫ
================================================================================

Правило: резать по бизнес-контексту; пока нет независимых деплоя/масштаба/команды — модульный монолит с пакетами-контекстами. Не god-service «на будущее». Не шарить БД при разрезании.

Что есть в fea (v360/fea-stage = prod):
Пакеты уже близки к целевому разрезу ТД:
  auth / account          — AuthN/RBAC
  organization            — компания / российская организация
  form-payment            — заявка и статусы (ядро)
  contract                — агентский договор
  file + generate-docs    — документы сделки
  payment / liquidity     — платежный контур
  recognition             — OCR/LLM (см. ML — это не ядро процесса)

Это не набор независимых сервисов, а Nest-модули одной БД (Mongo). По правилу это ПРАВИЛЬНАЯ стартовая форма: один деплой, явные пакеты.

fintech-platform ближе к «уже нарезанным» auth/kyc/payments/connectors, но:
- контексты чужие (банкинг/крипто-коннекторы, не агентский ВЭД);
- собирать платформу банка склеиванием этих сервисов = разрезать слишком рано и по слоям/инфре, не по ВЭД-возможности.

amg_all / коннекторы Striga, RailsR, Bitso — чужой bounded context (PSP). Имеет смысл только позже, как адаптер в контексте payments, с контрактом в бизнес-терминах заявки, не с прокидыванием внутренних DTO коннектора в UI.

exchange-* и _Exchange Platform — соседний продукт (обмен), те же слова FORM_* при другом процессе. Не база.

Решение по правилам: оставить fea монолитом. Резать только когда появится мотив (отдельная команда документов / отдельный масштаб коннекторов). Тогда резать по списку из правила, с явной транзакционной границей заявки — без shared Mongo «как сейчас».


================================================================================
3. ИНТЕГРАЦИЯ И СОБЫТИЯ
================================================================================

Правило: REST для команд; события — где sync склеивает сервисы; заявка = машина состояний на бэкенде; UI не единственный носитель статуса; платежи идемпотентны.

Совпадает с правилом:
- статусы и StageHash живут в fea (import/export × аванс/постоплата), не только во frontend;
- кабинеты бьют REST по ролям: site / internal-compliance-officer / compliance-officer / manager / provider / treasurer;
- очередь Bull: генерация отчёта агента, уведомления (асинхронные реакции документов);
- NATS в recognition/file — уже есть шина, но это внутренняя связность монолита, не публичный контракт.

Разрывы:
- PUT провайдера (payment/received, start, stop, sent, cancel) выставляет статус через updateByAdmins. Повторный клик / повтор доставки = риск повторного эффекта. Правило требует ключ идемпотентности / уникальность эффекта на деньги.
- Версионирование публичного API в кодовой базе не выглядит как явная политика совместимости — при стыке frontend stage с fea prod/main это уже проявилось (роль Internal CO).
- Нельзя чинить рассинхрон «статус только в UI»: frontend stage с кабинетом Internal CO при backend stage без роли — антипаттерн правила.

Решение: база — пара, где машина состояний на бэкенде покрывает роли ТД (fea prod или main). Frontend новее можно брать, но контракт ролей/статусов сверять как consumer-driven, не надеясь на одноимённые ветки.


================================================================================
4. БЕЗОПАСНОСТЬ РОЛЕЙ И ДАННЫХ
================================================================================

Правило ролей ТД: User / Internal CO / External CO / Manager / Provider.
AuthZ на сервисе, не только на gateway. Минимум данных. Provider — без ПДн клиента.

Совпадает:
- отдельные контроллеры и декораторы ролей (ProviderMethod и аналоги);
- зона видимости провайдера фильтруется provider: req.account._id;
- Internal CO есть на fea prod/main/develop/release_10 и во frontend stage/develop;
- External CO = COMPLIANCE_OFFICER.

Нарушения правила — блокеры, не «косметика»:

A) fea stage/dev удалили INTERNAL_COMPLIANCE_OFFICER.
   ТД и правило ролей требуют Internal CO (российские организации, первая заявка).
   Эту ветку нельзя объявлять «актуальным бэкендом под ТД» без возврата роли и контроллеров.

B) Provider GET отдаёт FormPaymentWithAgentProviderDto с полным account: IAccount.
   Это не минимум на границе. Для банка — доработать отдельный DTO: реквизиты, инвойс, сумма/валюта, хеш/платёжка, без ПДн клиента и лишней карточки организации.

C) TREASURER / ONE_C / ATTRACTION_MANAGER / LOGIST / SENIOR_PROVIDER — сверх ТД.
   Не запрещены правилом, но не ядро MVP. Не делать их обязательными в онбординге банка (UX: Hick / Pareto). Прятать или выключать, пока отдел их не запросил.

AuthN/AuthZ уже на Nest-модулях — это плюс относительно «всё на gateway». При будущем разрезе правило требует те же проверки на каждом новом сервисе.


================================================================================
5. УСТОЙЧИВОСТЬ И НАБЛЮДАЕМОСТЬ
================================================================================

Правило: корреляция по id заявки; при сбое провайдера заявка в ожидаемом статусе; ограниченные ретраи; сбой — штатный сценарий.

В fea:
- статусы PAYMENT_* позволяют оставить заявку в процессе при проблеме исполнения — это правильная деградация на уровне домена;
- очередь при ошибке делает throw → ретраи Bull. Лимиты/backoff нужно явно зафиксировать, иначе очередь усиливает каскад (генерация PDF, Anthropic, почта);
- логи процессора заявок завязаны на job.id, не на formPayment id — слабая корреляция сквозь mail/socket/recognition.

Кэш «на каждый модуль» в коде не выглядит как стратегия по умолчанию — это хорошо (правило: масштаб по нагрузке, не заранее).

Не тащить из amg/fintech тяжёлые цепочки sync-коннекторов в шаг смены статуса заявки. Коннектор — за очередью/адаптером, повтор идемпотентный.


================================================================================
6. МАШИННОЕ ОБУЧЕНИЕ
================================================================================

Правило: ML не в MVP ядра (роли, документы, флоу, статусы). Инференс за отдельной границей. Низкая уверенность → ручной review, не автоплатёж.

В fea recognition:
- Yandex OCR + Anthropic разбирают инвойс и пишут поля в заявку;
- вызов сидит в том же контуре, что перевод CREATING → DRAFT.

Это полезный ассистент, но по правилу это НЕ часть процессного ядра и НЕ транзакционный путь платежа.

При реализации для банка:
- статусы и обязательность полей — правила и state machine, даже если OCR молчит;
- recognition — отдельный модуль/джоба, срыв модели не двигает платёж и не обходит compliance;
- ChatGPT/Anthropic-разбор контрагента не заменяет Internal/External CO.

fintech KYC-скоринг и любые GPU-истории — вне MVP (лучшие-практики / тренды).


================================================================================
7. ПРАВИЛА ПОСТРОЕНИЯ, NEST, ТЕСТЫ
================================================================================

Правило: тесты к сервисам; unit + контракт API, не только E2E; после изменений проверять переходы статусов и право роли.

Факт по fea prod (v360): в src почти один *.spec.ts (currency). Контроллеры заявок, StageHash, роли — без автотестов.

Это главный инженерный риск «брать уверенно как продукт»: домен совпадает с ТД, воспроизводимость поведения — нет.

Минимум перед наращиванием фич банка (nestjs-testing + правила-построения):
- табличные unit на StageHash (импорт/экспорт × аванс/постоплата);
- unit на каждое действие роли (кто может PAYMENT_SENT, FORM_WAITING_CORRECTIONS, CANCELED_BY_*);
- контракт frontend↔fea на enum ролей/статусов (чтобы не повторить пару stage-UI / stage-API без Internal CO);
- Playwright — критичные кабинеты (не все 400 веток UI).

Не добавлять публичные admin/test эндпоинты.

По nestjs-modules: модуль на маршрут/роль уже есть; persistence — Mongoose (уже выбранный в проекте ORM, не менять «на TypeORM из правила»).


================================================================================
8. UX-ПРАВИЛА (как не ломать продукт при доработке)
================================================================================

Кабинеты frontend stage уже дробят процесс по ролям и стадиям (chunking, Hick, Goal-Gradient) — это оставлять.

Не делать:
- один экран со всеми статусами ТД и всеми сверх-ролями (treasurer, 1C, attraction);
- онбординг «все функции Fea360»;
- зависимость шага заявки от ожидания OCR без скелетона и без ручного ввода (Doherty + Postel: принять ручной ввод, нормализовать).

Jakob: кабинеты manager/compliance/provider уже привычная модель — не переписывать на fintech-admin с нуля.


================================================================================
9. ЧТО БРАТЬ / НЕ БРАТЬ (пересчёт приоритета)
================================================================================

Брать уверенно как домен ВЭД (с долгом из §§4–7):
1. fea @ prod (+ release_10) — аудит, роли ТД включая Internal CO, документы агента, import/export.
2. fea @ main — если нужны treasurer/senior_provider, но Internal CO сохранить.
3. frontend @ stage|develop — актуальные кабинеты ВЭД; сверять контракт с выбранным fea.
4. frontend @ release_10 / v360/frontend-stage — согласованная пара к fea prod.

Брать только как заимствование (не база процесса):
- design-system feature/* — UI-примитивы.
- fintech-platform — RBAC/KYC/коннекторы как референс адаптеров, после стабилизации монолита.
- amg_all — инфра и PSP-коннекторы в контексте payments.
- recognition в fea — как отделяемый ассистент, не как ядро.

Не брать как основу платформы банка по ТД:
- fea @ stage/dev — пока не возвращён Internal CO.
- frontend @ prod — Crypto 360.
- exchange-backend/frontend, _Exchange Platform — другой продукт.
- AMG / AMG-Flow / 360Flow / gitlab AMG — слабое пересечение с агентским ВЭД.
- нарезка микросервисов «как в fintech» на старте.

Практический план реализации (согласован с правилами, без лишней документации в коде):
1. Зафиксировать пару веток (рекомендация: fea prod + frontend stage, закрыть разрыв Internal CO на уровне контракта).
2. Покрыть тестами переходы и роли.
3. Сузить DTO провайдера.
4. Отвязать recognition от обязательного перехода статуса.
5. Идемпотентность payment-* и корреляция логов по id заявки.
6. Только потом — коннекторы/казначей/1C по запросу отдела.


================================================================================
10. ОГРАНИЧЕНИЯ
================================================================================

- Правила меняют приоритет архитектуры и долг, не отменяют скоринг веток.
- vd-audit на диске по-прежнему iCloud; эквивалент = v360 + fea prod.
- «Уверенно» = совпадение домена и ролей с ТД + соответствие границам/ролям; не = прогнанный банковский стенд.
