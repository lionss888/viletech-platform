# ПУНКТ 1. Соответствие вводным (ТЗ заказчика)

## 1.0. Общая картина

**Что означает «выполнены вводные» для заказчика:** пользователь каждой роли проходит описанные сценарии в **рабочем кабинете**, документы и статусы совпадают с ТЗ, деньги и роли защищены на сервере.

**Факт сейчас:**

- **Backend (~82–85% вводных на уровне API/домена):** машина статусов, роли, 331/331 маршрут parity, refund, bank channel, contracts R3, multi-order, file ACL, provider projection без ПДн.
- **Продукт (~55–60%):** UI (`vdp/fe`) — демо на `localStorage` + `mock.ts`, **не вызывает** `/api/v1/*`.
- **Разрыв:** заказчик не может принять «платформу ВЭД» по кабинетам, пока не закрыт FE↔API (см. часть A в связанном файле).

**Главный вывод пункта 1:** большинство пробелов в глазах бизнеса — не «дописать ещё 50 endpoint'ов», а **подключить UI к уже существующему API** и довести документы/интеграции на staging.

## 1.1. Роли в системе

Источник: «вводные от ви.txt», строки 3–8; расширение §7.

| Роль | Требование ТЗ | Backend (API/домен) | UI (fe) | На что влияет | Что нужно сделать |
|------|---------------|---------------------|---------|---------------|-------------------|
| **User** | Только свои заявки; создание, submit, документы, статус | **Готово:** `CanSeeForm`, list/get ACL, create, actions | **Не сделано:** mock, нет API | Нельзя UAT «клиентский путь»; приёмка User-блока ТЗ | FE: auth, `GET/POST forms`, create wizard → API |
| **Internal CO (ICO)** | Только РФ-организации; верификация org + первая линия по заявке | **Готово:** ICO actions, org approve, org queue | **Частично:** кнопки в demo `actions.ts`, локальная логика | ICO не проверен на prod-данных; риск ложной приёмки compliance | FE: очередь org, `ico_*` actions через bridge; Playwright ICO |
| **External CO (ECO)** | Иностранные орг./документы; после ICO | **Готово:** ECO flow, eco_* actions | **Частично:** demo only | ECO journey нет в browser E2E | FE + e2e reject-path на API |
| **Manager** | Все заявки; ПА, провайдер, договор, поручение, платёж, возврат, закрытие | **Готово:** широкий API, nest-parity routes | **Частично:** богатый demo UI, mock | Менеджер — центр ТЗ; без API это главный gap приёмки | FE: assign agent/provider, rate, contract, refund, report/shipment |
| **Provider** | Только assigned; инвойсы/реквизиты; **без ПДн клиента** | **Готово:** `ProjectForProvider`, `ForbiddenPIIKeys`, ACL tests | **Частично:** скрыта колонка «Клиент» в demo, но данные mock | Регуляторный риск если UI покажет ПДн из mock; prod — проверить projection API | FE: только `GET provider/...`; тест ACL в Playwright |
| **Admin / Root** | Шаблоны ПА, bank client type, аудит (расширение) | **Частично:** root accounts, bank org fields; шаблоны ПА в payload, не админка шаблонов | **Частично:** `/admin`, `/testing` на mock | Bank commission / template admin — продуктовый gap расширения | FE admin + API catalog; отдельный backlog |
| **Bank (API-роль)** | Создание заявок через API, не полноценный кабинет | **Готово:** `POST /api/v1/bank/forms`, channel | **Не сделано:** badge только в demo | Приёмка банка-партнёра — отдельный контур | OpenAPI, sandbox, webhook; FE badge из `channel` |

### На что влияет блок ролей в целом

- **Договор с заказчиком:** без FE на API нельзя подписать акт по «кабинетам ролей» — только по API/скриптам.
- **Compliance / аудит:** AuthZ на backend есть, но **не демонстрируется** в UI → заказчик видит «красивый прототип», не защищённую систему.
- **Support:** путаница «в демо работает, в проде нет» → рост L1 (см. rule `поддержка-и-обратная-связь`).

### Что нужно сделать (сводка по ролям)

1. Единый **app-контур** с JWT (`app-vs-demo.md` — сейчас только в доке).
2. **Action bridge** UI id → core HTTP (см. связанный файл, A.3).
3. **Playwright** минимум: User, ECO reject, Manager payment, Provider ACL, bank badge — на compose stack.
4. Матрица UAT: `vdp/docs/pilot/uat-scenarios.md` прогонять на API, затем на FE.

## 2.14. Итог пункта 2 — что требуется для «rules соблюдены»

**Для backend-поставки (текущий scope R0–R12):** в основном **да**, с оговорками observability deploy и security sign-off.

**Для продуктовой поставки заказчику:** **нет** — пока FE нарушает:
- `чистая-архитектура` (UI как источник истины),
- `безопасность` (нельзя доказать AuthZ в UI),
- `ui-web-практики` (нет «следующего шага» из домена),
- `тесты-архитектуры` (browser не на API),
- `поддержка` (demo ≠ prod создаст confused contacts).

**Минимальный план закрытия rules для prod:**

1. FE app-контур (JWT, API, bridge) — закрывает архитектуру + UX + тесты UI.
2. `security-signoff-checklist.md` на staging.
3. Deploy semantic alerts + один runbook drill.
4. Обновить `readiness-and-limits.md` с новыми %.
