## Как читать эту сводку одной минутой

На публичном стенде **alpha.vedy.io** сейчас **не одна ветка**.

- **Фронт** собран вручную с ветки **`d0-1`** (выравнивание UI с Lovable).
- **Бэкенд** (core, hub, docs) — штатные образы с ветки **`main`**.
- Tip ветки **`d0-1` уже ушёл дальше** (уведомления, чаты, 1С/Диадок/шлюзы) — **на alpha этого нет**.
- Lovable **`dev0`** (`lionss888/vdp`) — **не та же ветка**, что `d0-1`. Это эталон демо-UI, с которого портировали внешний вид.

### А.3. Гибрид: согласован ли фронт с бэком на alpha?

**Да, для того среза, который выкатили.**

Расхождение начнётся, если выкатить **только** новый фронт из `f1e39cba` на старый бэк: кнопки чатов/профиля/notify упрутся в отсутствие маршрутов core. Сейчас этого на alpha нет.

Ветки **https://github.com/lionss888/viletech-platform**:

| Ветка | Tip (на 2026-09-01) | На alpha? |
|-------|---------------------|-----------|
| **`main`** | `650e1f0e` | **бэкенд — да**; фронт — **нет** (на `main` нет коммита Lovable-выравнивания) |

Три коммита `d0-1`, которых нет в `main`:

## 1. Дыры (что реально не закрыто)

Ниже — не «весь бэклог мира», а то, на что опираться, чтобы не планировать из ложного «уже готово».

### 1.1. Продукт vs вводные (то, что заказчик ожидает в кабинете)

- **Матрица действий живёт во фронте** (`vdp/fe/src/lib/ved/actions.ts`), core **не отдаёт** `allowed_actions` в GET заявки. Правило платформы: UI — проекция, истина — домен. Сейчас кнопка может существовать в UI и получить 403 с сервера (или наоборот). Это главная архитектурная дыра app-контура.
- **Удаления документа в app нет** (в демо есть). Загрузка в app требует реальный файл.
- **Паритет demo ↔ app не 100%.** Матрица в `vdp/fe/AGENTS.md`.
- **Playwright** покрывает узкий набор journey (happy-path, reject, provider ACL, bank badge, login, manager-payment), не все роли × все статусы. Сквозной UI до `completed` не полный.
- Открытые вопросы ТЗ (ещё не закрыты заказчиком в вводных): отчёт при N поручениях, `REPORT_ACCEPTED`, порядок выбора ПА и курса, конфликт «Provider видит ИНН» vs запрет ПДн.

### 1.2. Интеграции наружу (stub / fixture, не боевой вендор)

| Контур | Что есть | Чего нет |
|--------|----------|----------|
| **1С** | Порт hub `cover`/`fee`, smart stub, callback в core без автоплатежа | Живой `ONEC_URL`, приёмка бухгалтерией. **С 2026-09-01 во вводных: 1С под вопросом** — не блокер пилота, пока не снимут |
| **Диадок** | Контракт + stub + UI статуса; ручной путь сохранён | Боевой вендор не обязателен для пилота (решение B.2) |
| **Банк как партнёр (§5)** | Внутренний канал `channel=bank`, JWT роль `bank`, идемпотентный create, HMAC webhook | Нет партнёрского OpenAPI, sandbox, machine AuthN, live-badge. Отчёт: `заметки/vdp-bank-api-gap-2026-09-01.md` |
| **Почта / SMS** | Код gateway на `d0-1` (`f1e39cba`) | На alpha образов gateway **нет**; без URL hub остаётся на stub |
| **Telegram** | Код на `d0-1` | На alpha нет; без токена — fixture |
| **OCR** | Опциональный side-path; `recognize_complete` без вендора двигает черновик | Не на пути commit платежа (так и должно быть) |
| **PDF / шаблоны ПА** | docs-service отдаёт **минимальный PDF** (почти текстовый заголовок), не юридический бланк | Pixel-fidelity и подпись шаблона юристом — открыты |

### 1.3. Деплой и ветки

- Alpha **не** является снимком одной ветки.
- Tip `d0-1` (`f1e39cba`) **не задеплоен**.
- Канонический CD с `d0-1` не прошёл (нет admin на `workflow_dispatch`; `main` не fast-forward).
- GitHub Environments / gamma promote / K8s — не закрыты как «прод-конвейер».

### 1.4. Наблюдаемость

В репозитории есть structured logs, черновики semantic alerts и runbooks. **Развёрнутого Prometheus/алертов на alpha как рабочего on-call контура нет.** Формальный security sign-off не подписан (`vdp/docs/operations/security-signoff-checklist.md` — все пункты «не выполнено»).

### 1.5. Честно не дыры, а осознанный out of scope

Логистика, аналитика, ассистент, полный BDUI-движок, миграция данных из Nest-монолита. Зелёный Nest-mapping 331/331 = **маршруты**, не полный Nest как продукт.

## 2. Качество проекта в целом

Оценка **на 2026-09-01**, без ложного «готово на 100%».

| Срез | Честная оценка | Почему так |
|------|----------------|------------|
| **Домен core (статусы, роли, платежный путь API)** | сильный для пилота | Машина статусов в Go, AuthZ на endpoint, e2e API, отдельные Postgres core/hub, outbox |
| **Кабинет как продукт** | средний | App уже на JWT; визуал выровнен с Lovable на alpha; глубина UI и серверная матрица действий ещё дырявые |
| **Внешние системы** | слабый / stub-first | Вендоры за портами; без URL — fixture. Это нормальная архитектура, но не боевая готовность |
| **Тесты** | сильные на backend, узкие на UI | Unit/HTTP/compose-e2e; FE vitest + десяток Playwright. Пирамида правильная, вершина тонкая |
| **Поставка** | конвейер есть, дисциплина нарушена вручную | GHCR + digest + SSH задуманы хорошо; последний FE ушёл в обход |
| **Документы и правила** | сильные как каркас | `.cursor/rules`, честность готовности; часть заметок (мастер 31.08) отстала от кода |

Грубо, чтобы планировать, а не спорить о процентах:

- **Показать пилот на alpha (логин, заявка, роли, демо-UI):** можно, с оговорками.
- **Отдать заказчику как «полный паритет Lovable + Nest + 1С + банк»:** нельзя.
- **Go-live прод:** рано (файлы в RAM, нет sign-off, нет партнёрских контуров, гибридный деплой).

Качество **кода ядра** выше, чем качество **склейки продукт+ops+вендоры**. Не путать зелёный `make test` с готовым бизнесом.

## 3. Рекомендации (и на что они направлены)

Не backlog на спринт, а направления, чтобы следующие инструкции не разъезжались.

### 3.1. Вернуть alpha к одной понятной линии поставки

**Зачем:** чтобы ответ «что на стенде» снова был одной веткой, а не гибридом.  
**Как по смыслу:** либо merge `d0-1` → `main` (с осознанием, что `f1e39cba` тащит уведомления и шлюзы), затем `vdp-images` + `vdp-deploy`; либо явно зафиксировать «alpha = main + ручной FE `7948d683`» до следующего promote.  
**Не делать:** снова тихий rsync FE без pin, который расходится с GHCR.

### 3.2. Не выкатывать tip `d0-1` кусками

**Зачем:** фронт `f1e39cba` без того же бэка сломает чаты/notify.  
**Как:** FE и core/hub этой волны — одним релизом, либо не трогать alpha, пока волна не нужна на показе.

### 3.3. Серверная матрица действий

**Зачем:** убрать главный разрыв с правилами (UI ≠ истина статуса).  
**Направлено на:** core отдаёт допустимые действия роли; FE рисует только их; клиентская `actions.ts` перестаёт быть каноном в app-режиме.

### 3.4. 1С не планировать, пока не снимут вопрос

**Зачем:** не жечь волну на стенд 1С. Зафиксировано во вводных. Порт в коде можно не выкидывать.

### 3.5. Банк партнёру не обещать

**Зачем:** внутренний bank-контур ≠ OpenAPI для банка. Следующая волна банка — контракт + machine identity, не «допилить UI».

### 3.6. Файлы вынести из памяти процесса

**Зачем:** иначе рестарт `core` на alpha **стирает содержимое загрузок** (метаданные в Postgres остаются, байты — нет). Это блокер любой серьёзной UAT с документами. См. раздел 4.

### 3.7. Lovable: эталон `dev0`, не подмена продукта

**Зачем:** очередной sync не должен снести `lib/api` и JWT. Порт дельт в `pages` + `nav-config`; `mock.ts` не править под демо — только overlay.

### 3.8. Подписать security checklist до «отдали в тест с деньгами»

**Зачем:** роли и запрет ПДн у Provider уже тестируются кодом; формальной приёмки нет. Направлено на доверие заказчика, не на новые фичи.

## 4. Хранение данных и файлов

Это самый недооценённый риск пилота, если показывать загрузку документов.

### 4.1. Базы (структурированные данные)

Две **отдельные** Postgres: `postgres-core` и `postgres-hub` (разные URL, shared DB запрещён правилами).  
`STORE_DRIVER=postgres` на compose/alpha. Memory-store — только быстрые unit-тесты.

В core: заявки, аккаунты, организации, контрагенты, договоры, **метаданные файлов** (таблица `files`: id, owner, form_id, storage_key, content_type, content_hash), банк-настройки, outbox событий и т.д.

В hub: inbox/идемпотентность адаптеров, не канонический статус заявки.

Бэкапы и шифрование at rest на alpha **не зафиксированы как выполненная ops-процедура**.

### 4.2. Содержимое файлов (байты)

Контракт: интерфейс `BlobStore` (Put/Get/Delete) в `vdp/core/internal/storage`. Комментарий в коде: «S3-compatible stub OK».

**Реализация одна: `MemoryBlobStore`.** Загрузка пишет байты в map в процессе core, плюс строку метаданных в Postgres.

Следствия, которые нужно держать в голове:

- **Рестарт контейнера `vdp-core` → файлы нельзя скачать**, preview вернёт «не найдено», хотя запись в `files` останется.
- Несколько реплик core **не разделят** файлы.
- Это не S3/MinIO и не диск. Для пилота «потыкать UI» сгодится; для UAT документов и любого прода — **нет**.

Лимит загрузки в API около **15 МБ** (волна B.2). ACL preview: чужой `file_id` → 403 (есть unit). Удаления файла в app-API нет.

### 4.3. Генерация PDF (docs-service)

Отдельный контейнер. По `DOCS_URL` core просит сгенерировать документ. Сейчас сервис собирает **минимальный PDF** с комментариями полей, не бланк агентского договора. Без `DOCS_URL` hub/docs идут в stub (`docs/{id}/stub.pdf`). Юридическая верстка шаблонов по ПА — не закрыта.

### 4.4. Демо-контур фронта

`/demo/*` хранит состояние в **localStorage** браузера (`ved-demo-state-v2`), не в Postgres. Это не данные платформы. Seed демо патчится overlay’ем (другие email, лишняя форма) — только demo.

App-контур читает core. Не смешивать при разборе «пропали заявки»: сначала спросить, какой URL — `/demo` или JWT.

## 5. Безопасность

### 5.1. Что уже сделано разумно

- AuthZ **на API**, не только скрытие кнопок. Чужая роль / чужая заявка → 403.
- Роли ВЭД: User свои; ICO/ECO свои зоны; Manager широко; Provider — assigned, **DTO без ключей ПДн** (`ForbiddenPIIKeys`).
- События notify проверяются на запрещённые ключи ПДн.
- На не-локальных `ENVIRONMENT` (включая `alpha`) процесс **не стартует** с дев-секретами `vdp-core-dev-secret` / `vdp-s2s-dev-secret`.
- На alpha сервисы задуманы за Caddy: снаружи 80/443, core/hub/БД на loopback.
- HTTPS на домене (JWT и документы не должны идти открытым HTTP).
- Bank webhook: HMAC-SHA256 (секрет всё равно нужно держать вне git).
- Rate limit на gateway (конфиг `GATEWAY_RATE_LIMIT`).
- S2S core↔hub: `HUB_SHARED_SECRET`.

### 5.2. Что не закрыто / риск для планирования

- **Чеклист security-signoff не подписан** — формально «не выполнено» по всем пунктам, даже если часть уже в тестах.
- **Файлы в RAM** — потеря и невозможность аудита вложений после рестарта; нет шифрования blob at rest, потому что нет store.
- **Банк:** тот же JWT IdP, что у кабинетов, роль `bank`. Нет mTLS, API key, отдельного audience. Для партнёра недостаточно.
- **1С-роль в домене есть**, полноценного внешнего IdP 1С нет; и контур под вопросом.
- Ротация секретов, vault, шифрование бэкапов — ops, не закрыто документом.
- `workflow_dispatch` образов требует **admin** — поставка завязана на права человека, не только на CI.
- Репозиторий GitHub **public** (`lionss888/viletech-platform`). Секреты не должны попадать в git; seed-пароли стенда считать известными для demo, не для прод-клиентов.
- Конфликт ТЗ: Provider «видит ИНН» vs запрет ПДн — не разрешён заказчиком; код сейчас режет набор ключей, не «всё что захочет UI».

### 5.3. Практический вывод по безопасности

Для **закрытого показа** на alpha с сид-аккаунтами: контур приемлемый (HTTPS, не-дев JWT, RBAC).  
Для **реальных ПДн и денег**: рано — нет постоянного file store, нет sign-off, банк/1С не в боевом AuthN, наблюдаемость инцидентов не доведена до дежурства.
