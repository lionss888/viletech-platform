Флоу оплаты ВЭД
Источник: FigJam «Флоу оплаты ВЭД» (https://www.figma.com/board/2E5CNEhFc4cJWK7Gx8d3H7)
Назначение: дополнение к «вводные от ви.txt» — требования с доски, которых нет или недостаточно во вводных ВИ. Документ для проектирования домена, API, статусов и UI.

Связь с базовыми вводными
	•	Базовый флоу заявки, роли и поля документов — в «вводные от ви.txt».
	•	Этот документ фиксирует расширения: типы договоров и шаблоны по ПА; загрузка договора менеджером; доп. поручение (аванс/постоплата); возврат ДС клиенту; канал банк/API; импортные маршруты аванс и POSTPAY_RATE_ON_PP (секция 10, источник — «Маршрут постоплатный импорт»).
	•	При конфликте формулировок приоритет уточняется с разработчиком; до согласования считать правила в «вводные от ви.txt» обязательными для реализации расширений.
	•	Исключение по деньгам: для импорта с platform_postpay_mode = POSTPAY_RATE_ON_PP порядок «провайдер до рублей клиента» из секции 10 и §3.6 переопределяет общее правило §3.6 «клиент платит до провайдера».

────────────────────────────────────────
1. Типы договоров и шаблоны по платёжному агенту (ПА)
────────────────────────────────────────

1.1. Цель
Гибкая работа с договорами между клиентом и агентом: разные типы, разные шаблоны в зависимости от выбранного ПА, учёт организации, от имени которой подана заявка.

1.2. Типы договоров
Поддерживаются три типа.

1.2.1. Агентский договор (стандарт)
	•	Стороны (модель сущностей на доске):
		•	account — участник организации клиента;
		•	organization — организация клиента (принципал);
		•	agent — организация агента (платёжный агент).
	•	Сценарий как в базовых вводных: шаблон скачивается клиентом, подписывается, загружается на платформу; менеджер подтверждает.
	•	После подтверждения договор действует для последующих заявок этой организации с тем же агентом (пока не деактивирован / не отправлен на коррекцию).

1.2.2. Субагентский договор
	•	Стороны:
		•	account — клиент (субагент);
		•	organization — организация, от лица которой выступает клиент;
		•	agent — организация агента.
	•	Прикрепляет менеджер (см. раздел 2).
	•	После подтверждения субагентского договора отдельный агентский договор для последующих заявок этой организации не требуется.
	•	На карточке заявки обязательно поле «Организация от имени которой подана заявка» (см. 1.5).

1.2.3. Договор на оказание услуг
	•	Прикрепляет менеджер.
	•	При прикреплении указывается учётная запись (не организация): «договор на оказание услуг загружает менеджер — не организация, а учётная запись; расширить поле имя компании».
	•	Название учётной записи отображается в заявке рядом с организацией клиента и при подаче заявок.
	•	Дополнительно для каждой организации клиента по-прежнему требуется агентский договор, если он ещё не был прикреплён и подтверждён ранее.

1.3. Шаблоны по платёжному агенту
	•	Единый шаблон на всю платформу недостаточен.
	•	У каждого ПА свой шаблон (или набор шаблонов) агентского договора.
	•	Правило отображения: после выбора менеджером платёжного агента в заявке клиенту показывается шаблон, соответствующий этому агенту.
	•	Администрирование: привязка шаблона(ов) к карточке ПА в админке; версия/дата шаблона желательна для аудита.

1.4. Состояния договора в заявке (ветвление менеджера)
На доске: после выбора ПА и провайдера — проверка наличия агентского договора. Ветки:
	•	Договор есть и подтверждён → переход к формированию поручения (статус области FORM_ACCEPTED / далее SIGNING_ORDER*).
	•	Договор есть, но не подтверждён → CONTRACT_VERIFICATION (ожидание/проверка).
	•	Договор есть, но деактивирован или на коррекции → CONTRACT_WAITING_CORRECTION.
	•	Договора нет → CONTRACT_WAITING (клиент скачивает/подписывает/загружает, либо менеджер прикрепляет вручную).

Действия менеджера на проверке договора:
	•	Подтвердить наличие договора.
	•	Вернуть клиенту для уточнений.
	•	Отклонить сделку (CANCELED_BY_MANAGER).

1.5. Заявки от имени другой организации
Сценарий (субагент и смежные кейсы):
	•	Клиент подаёт заявку от своей организации, но сделка инициирована/заказана другой организацией.
	•	На карточке заявки: редактируемое поле «Организация от имени которой подана заявка» (иконка редактирования).
	•	То же поле видно менеджеру в карточке организации внутри заявки.
	•	Валидации: уточнить обязательность поля для типа «субагентский»; для агентского — поле может быть скрыто или необязательно.

1.6. Требования к карточке организации
	•	Отображение текущего типа договора (агентский / субагентский / услуги).
	•	История прикреплённых договоров (аудит).
	•	Возможность смены типа договора администратором вручную.

1.7. Открытые вопросы для реализации
	•	Кто может добавлять пользователя в организацию (узел на доске без ответа) — зафиксировать роль (владелец орг. / менеджер / админ).
	•	Нужен ли отдельный статус сущности «договор» вне заявки (active / pending / deactivated) vs только статусы заявки CONTRACT_*.
	•	«Зеркальный договор купли-продажи» на стикере — вне scope этого документа, пока нет ТЗ.

────────────────────────────────────────
2. Загрузка договора менеджером с авто-подтверждением
────────────────────────────────────────

2.1. Цель
Менеджер может прикрепить договор, полученный вне платформы (скан, почта, встреча), без ожидания загрузки/подписи клиентом в UI.

2.2. UI / действия
	•	Кнопка: «Прикрепить договор вручную» (в карточке заявки / организации — уточнить место в макетах).
	•	Обязательный выбор типа договора: агентский / субагентский / оказание услуг.
	•	Для типа «оказание услуг» — обязательное поле учётной записи / имени.
	•	Загрузка файла (PDF; лимит согласовать с базовыми вводными, ориентир 15 МБ).

2.3. Поведение после загрузки менеджером
	•	Автоматическая активация статуса «договор подтверждён» (эквивалент ветки «Договор есть и он подтвержден»).
	•	Пропуск шага ожидания скачивания / подписания / загрузки со стороны клиента.
	•	Заявка продолжается к формированию поручения принципала (если остальные условия выполнены: ПА, провайдер, данные сделки).

2.4. Ограничения и аудит
	•	Фиксировать в истории: кто загрузил, когда, тип договора, исходный статус заявки.
	•	Клиент должен видеть факт наличия подтверждённого договора (без обязательного повторного подписания в этом сценарии).
	•	Отзыв / деактивация договора — только явным действием менеджера/админа с переводом связанных заявок в CONTRACT_WAITING_CORRECTION при необходимости.

2.5. Связь с клиентским путём
Клиентский путь (скачать шаблон → подписать → загрузить) остаётся основным для агентского договора, если менеджер не использовал ручную загрузку.

3. Дополнительное поручение принципала (аванс / постоплата)
────────────────────────────────────────

3.1. Цель
Одно поручение на сделку может быть недостаточным при смешанных или двухэтапных условиях оплаты (аванс + остаток / постоплата). На доске: основное поручение + «Доп. поручение принципала».

3.2. Базовое поручение (напоминание из ВИ + доска)
	•	Формируется менеджером (или автоматически, если заданы комиссия и условия) после подтверждённого договора.
	•	Менеджер указывает комиссию и курс; поручение генерируется / прикрепляется.
	•	Отправка клиенту на подписание → проверка менеджером → SIGNING_ORDER_ACCEPTED (и смежные статусы SIGNING_ORDER_*).
	•	Импорт и экспорт: формируются разные поручения (разные шаблоны/поля — заложить в генератор документов).

3.3. Когда создаётся доп. поручение
По согласованию с клиентом менеджер может выбрать:
	•	постоплату (отдельная ветка на доске «Заявка с постоплатой»);
	•	авансовую оплату с последующим доп. поручением на остаток / следующий этап.
Статусы на доске для авансового доп. контура:
	•	ADVANCE_SIGNING_ORDER
	•	ADVANCE_SIGNING_ORDER_WAITING_VERIFICATION
	•	ADVANCE_SIGNING_ORDER_WAITING_CORRECTIONS
	•	ADVANCE_SIGNING_ORDER_ACCEPTED

3.4. Действия менеджера по доп. поручению
	•	Сформировать дополнительное поручение.
	•	Указать комиссию / курс (если отличаются от основного).
	•	Загрузка / прикрепление доп. поручения.
	•	Отправить клиенту на подписание.
	•	Отозвать поручение (как у основного).
	•	Подтвердить доп. поручение клиента.
	•	Вернуть доп. поручение клиенту на уточнение.
	•	Сформировать новое поручение (после отзыва / коррекции).
	•	Приостановить проверку / прекратить проверку — по аналогии с основным контуром.

3.5. Действия клиента
	•	Скачать / ознакомиться / подписать.
	•	Отправить (загрузка подписанного доп. поручения).
	•	При необходимости — прикрепить подтверждение платежа (опционально), как в основном контуре.

3.6. Связь с оплатой и исполнением
	•	Общее правило (аванс и доп. поручения без режима POSTPAY_RATE_ON_PP): после принятого поручения (основного или доп.) клиент переводит средства агенту; менеджер и/или казначей подтверждают получение средств; менеджер указывает срок исполнения и отправляет заявку провайдеру (детали казначея на импорте — секция 10).
	•	Исключение — импорт с platform_postpay_mode = POSTPAY_RATE_ON_PP: порядок денег из документа «Маршрут постоплатный импорт» и секции 10 переопределяет правило выше. Провайдер исполняет валютный платёж и прикладывает ПП до рублёвого покрытия клиента; курс и доп. поручение формируются после ПП; клиент платит рубли после подписи доп. поручения; затем казначей подтверждает ДС.
	•	Для постоплаты / отгрузки на доске есть контур SHIPMENT_* (SHIPMENT_WAITING, SHIPMENT_VERIFICATION, SHIPMENT_WAITING_CORRECTIONS, SHIPMENT_WAITING_VERIFICATION) и закрывающие документы — стыковать с базовым шагом закрывающих из ВИ (не путать SHIPMENT_* с денежным порядком RATE_ON_PP).

3.7. Правила для платформы
	•	Одна заявка может иметь несколько поручений (основное + N дополнительных); у каждого — свой жизненный цикл статусов и файлов.
	•	Провайдеру на исполнение уходит актуальный принятый пакет (какое поручение «активно» для текущего платежа — явно хранить в домене).
	•	Отчёт агента формируется после исполнения релевантного платежа; при нескольких платежах — уточнить: один отчёт на заявку или отчёт на каждое поручение (открытый вопрос).

4. Возврат денежных средств клиенту
────────────────────────────────────────

4.1. Цель
Если сделка сорвалась после поступления средств (отклонение поручения, отказ провайдера, ошибка реквизитов и т.п.), менеджер инициирует возврат ДС клиенту.

4.2. Точки входа (с доски)
	•	После проверки поручения: действие «Возврат денежных средств клиенту».
	•	Ветки отклонения / прекращения проверки поручения могут вести к возврату, если средства уже получены.

4.3. Статусы (с доски)
	•	PAYMENT_REFUND_WAITING — ожидание начала / подготовки возврата.
	•	PAYMENT_REFUND_PROCESSING — возврат в процессе.
	•	PAYMENT_REFUND_SENT — возврат исполнен / отправлен.

4.4. Сценарий менеджера
	1. Страница процесса возврата денежных средств.
	2. «Начать процесс возврата» → PAYMENT_REFUND_PROCESSING.
	3. Опционально: прикрепить файл подтверждения возврата.
	4. «Подтвердить возврат ДС» → PAYMENT_REFUND_SENT / «Возврат денежных средств исполнен».
	5. Альтернативы:
		•	«Отменить процесс» — выход без возврата (вернуться в предыдущий осмысленный статус заявки).
		•	«Прекратить возврат» — прервать начатый возврат.

4.5. Данные и контроль
	•	Сумма и валюта возврата сверяются с фактически поступившими средствами по заявке.
	•	Реквизиты возврата — на клиента / организацию плательщика (уточнить источник: карточка компании vs реквизиты из платёжки).
	•	Возврат не должен открывать провайдеру ПДн сверх базового правила ВИ.
	•	История: кто инициировал, подтвердил, какие файлы приложены.

4.6. Связь с отменой сделки
	•	CANCELED_BY_MANAGER / CANCELED_BY_COMPLIANCE_* / CANCELED_BY_USER — если деньги уже на стороне агента, отмена без возврата недостаточна: нужен явный контур возврата или статус «ожидает возврата».
	•	Зафиксировать инвариант: нельзя перевести заявку в финальный CANCELED_*, пока есть невозвращённый остаток (или явно пометить «списание/удержание» отдельным действием — out of scope, пока нет ТЗ).

5. Банк / API
────────────────────────────────────────

5.1. Цель
Отдельный канал клиента: не только UI платформы ВЭД, но и банковский / партнёрский сервис (на доске пример: «КОНОПУС»), который передаёт детали заявки через API.

5.2. Участники и поток
	•	Клиент работает в сервисе банка.
	•	Выбирает организацию плательщика у себя на платформе банка.
	•	Детали заявки передаются на платформу ВЭД через API.
	•	Дальше заявка живёт в тех же ролевых контурах (комплаенс → менеджер → провайдер), с отличиями по комиссии/курсу и генерации поручения.

5.3. Тип клиента «Банк» (админка)
	•	Комиссия известна заранее: админ выставляет комиссию в админке при выборе типа клиента «Банк» (обязательное поле).
	•	Курс по умолчанию подставляется без наценки платформы.
	•	В админке при настройке типа клиента — переключатель: «Применять наценку платформы на курс?» (да/нет).
	•	От этого зависит, что уходит в поручение и что видит менеджер (редактируемость курса/комиссии — уточнить: для «Банк» поля могут быть read-only).

5.4. Автоматизации на доске (ветвление)
Узлы принятия решений / автопроверок, релевантные API-каналу и ускоренному пути:
	•	Организация клиента подтверждена?
	•	Есть активный контракт с агентом?
	•	Есть прошлая заявка, где с агентом был заключён контракт?
	•	Прошёл проверку ТН ВЭД код?
	•	Проверка заявки внутренним / внешним комплаенсом.
	•	Установка агента по умолчанию.
	•	Автоматическая генерация поручения принципала и отправка клиенту — если комиссия уже выставлена и поручение ещё не сформировано.
	•	Альтернатива: генерация поручения менеджером вручную.

5.5. Требования к API (для проектирования контракта)
Минимальный контур (из смысла доски; детальный OpenAPI — отдельная задача):
	•	Идемпотентное создание/обновление заявки из банка (ключ идемпотентности).
	•	Передача: организация плательщика, контрагент, сумма/валюты, инвойс/контракт (ссылки или файлы), назначение, условия оплаты.
	•	Ответы со статусом заявки и deep-link / correlation id для банка.
	•	AuthN/AuthZ отдельного технического клиента банка; зона видимости — только заявки этого канала.
	•	События наружу (webhook или poll): смена статуса, запрос на подписание, запрос документов — чтобы банк мог продолжить UX у себя.

5.6. UI на стороне ВЭД для bank-заявок
	•	Менеджер видит источник заявки (канал: UI / Bank API).
	•	Организация агента может подставляться автоматически (на доске: «Проландия» как пример).
	•	Клиентский UI платформы ВЭД может быть урезан: часть шагов выполняется в банке.

	•	REPORT_WAITING_VERIFICATION

7. Роли и зона ответственности (только для расширений)
────────────────────────────────────────

	•	User (клиент): подпись поручений (основное/доп.), оплата, опциональные чеки; при субагенте — указание организации «от имени»; в bank-канале часть шагов в банке.
	•	Manager (клиентский менеджер в «Маршрут постоплатный импорт»): выбор ПА/провайдера; ручная загрузка договора + тип; курс/комиссия; основное и доп. поручения; возврат ДС; отчёт и закрывающие; не подменяет казначея на подтверждении рублёвого покрытия.
	•	Treasurer (казначей): на импорте подтверждает заход рублёвого покрытия клиента и передачу заявки в работу провайдеру (со сроком исполнения) — см. секцию 10. Не задаёт курс и не формирует поручение вместо Manager. Экспортный смысл казначея (PAY_FROM_EXPORT / overpay) — вне scope импортного аддендума (§8).
	•	Admin: шаблоны договоров по ПА; тип клиента «Банк» (комиссия, переключатель наценки); смена типа договора; аудит.
	•	Provider: без изменений базового правила ВИ (нет ПДн клиента); исполняет платёж по актуальному поручению.
	•	Compliance (ICO/ECO): без изменений ядра из ВИ; doc «Маршрут постоплатный импорт» их не отменяет; bank-заявки проходят те же проверки, если авто-условия не закрыли этап.

10. Импорт: аванс и RATE_ON_PP
────────────────────────────────────────

Источник: «вводные/Маршрут постоплатный импорт.docx» (Client Journey, импортная сделка).
Назначение: зафиксировать денежные и документные инварианты двух маршрутов до реализации в VDP. ICO/ECO, агентский договор, выбор ПА — по «вводные от ви.txt»; этот раздел их не отменяет.

10.1. Общая схема сделки
	•	РФ-клиент платит рубли на счёт агента в РФ; иностранный агент (И-агент / исполнение через ПА и провайдера) платит валютой поставщику клиента.
	•	«И Агент» в doc = сторона исполнения / счёт в контуре ПА; в платформе — выбор Manager’ом платёжного агента и провайдера (не путать с агентским договором принципала).

10.2. Маршрут аванс (импорт)
	1. Manager фиксирует курс обмена и агентское вознаграждение (режимы — 10.5) → формируется поручение.
	2. User проверяет и подписывает поручение, загружает скан, производит оплату в рублях.
	3. Manager проверяет подписанное поручение.
	4. Treasurer подтверждает заход рублёвого покрытия на счёт агента и передаёт задачу провайдеру, проставляя срок исполнения.
	5. Provider исполняет платёж со счёта И-агента поставщику, прикрепляет ПП; при вопросах — возврат Manager’у.
	6. Manager формирует отчёт о сделке (номер и дата ПП); User подписывает; Manager подтверждает.

10.3. Маршрут постоплата с курсом в день ПП (POSTPAY_RATE_ON_PP)
	•	На заявке: direction = import, payment_method / условие постоплаты, platform_postpay_mode = POSTPAY_RATE_ON_PP (rate_on_provider).
	1. Manager формирует primary-поручение с реквизитами поставщика: допускается фиксация процента вознаграждения БЕЗ курса.
	2. User подписывает и загружает поручение; Manager принимает и передаёт в работу Provider (без ожидания рублёвого покрытия клиента).
	3. Provider исполняет платёж, прикрепляет ПП; при вопросах — возврат Manager’у.
	4. После ПП Manager фиксирует курс и вознаграждение (10.5) → формируется дополнительное поручение (контур ADVANCE_*).
	5. User подписывает доп. поручение, загружает скан и производит оплату в рублях.
	6. Manager проверяет доп. поручение; Treasurer подтверждает поступление ДС в рублях от клиента.
	7. Закрывающие / отчёт — как в 10.2 п.6.

	Инвариант: для POSTPAY_RATE_ON_PP провайдер исполняет валютный платёж раньше рублёвого покрытия клиента. Это переопределяет общее правило §3.6 (см. также введение документа).

10.4. Роли (маппинг doc → платформа)
	•	РФ Клиент → User
	•	Клиентский менеджер → Manager
	•	Казначей → Treasurer (импортное покрытие; не только export)
	•	Провайдер → Provider (без ПДн клиента; реквизиты платежа, инвойс, id заявки, ПП/хеш)
	•	ICO / ECO / договор / ПА — по ВИ; в doc не описаны, но обязательны в полном journey

10.5. Агентское вознаграждение (контракт для реализации)
Три режима выбора Manager’ом при фиксации условий поручения:
	•	Фиксированная сумма вознаграждения
	•	Процент от общей суммы
	•	Процент + фиксированное вознаграждение
В IMP0 только продуктовый контракт; домен/UI — отдельный этап реализации.

10.6. Открытые вопросы
Нет блокирующих: приоритет §3.6 для RATE_ON_PP и роли казначея на импорте зафиксированы. Уточнения шаблонов PDF primary без курса и точных статусов казначея — на этапах реализации (не блокируют ТЗ).
